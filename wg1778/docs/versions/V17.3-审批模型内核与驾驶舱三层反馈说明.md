# V17.3 审批模型内核与驾驶舱三层反馈说明

当前代码基线：**18.3.4 / V17.3**。

本版依据审批模型内部逻辑规则和驾驶舱最新规则，将原有“有界面、弱判断”的审批模型补成数字化库驱动的判断运算模型，同时重构驾驶舱的待办/已办/办结语义。

## 1. 审批模型内核

审批模型继续作为全系统通用独立模型，不嵌入任何具体业务模型。运行时读取前序业务数字化库的 `identifier_values`，并按需读取：行政审批层级、技术审查层级（历史业务审批层级兼容）、岗位分选、审批分管、审批阈值、人员信息、组织职级、审批意见、模型时限等标准数字化库。

审批模型形成：阈值变量集合、行政最终层级、技术审查最终层级、实际审批/审查人员、正式审批路径、总环节、当前环节、当前审批人、到达/到期时间、审批意见和审批过程。行政路径与技术审查路径拼接后按实际人员去重，并保留靠后的有效环节。

审批意见由审批意见标准数字化库提供；后端同时校验允许动作和终止属性。不同意或被标准库标记为终止的意见直接结束审批；同意且仍有下一环节时只产生下一环节待办。历史 `Q=0.5` 不恢复为通用审批状态，会议类特殊后续由审批归档后的智选模型决定。

审批模型最终继续只向审批模型自己的数字化库写入结果，并由审批数字化库的硬性链接触发智选模型。当前没有正式分配独立16位数字化标识的内部过程字段继续存储在审批过程/输出 JSON 中，不由代码编造编号。

## 2. 驾驶舱三层结构

驾驶舱改为三类一级能力：

1. **人与系统的交互**：系统开发=四阶段模型建设；系统运行=使用已发布模型。
2. **系统对人的反馈**：待办、已办、办结。
3. **系统对个人的约束**：今日办结模型、今日有效工作记录、今日已办理任务、今日数字化成果数排名以及公共资源服务。

统计数据由后端基于真实 `digital_library_records`、`model_runs` 和 `todos` 计算，前端不维护演示统计值。

## 3. 待办、已办、办结语义

- **待办**：当前需要本人处理的模型或模型环节。
- **已办**：本人已经完成过办理动作的任务/环节，只表示“人的办理记录”。
- **办结**：单个模型自身已完成并归档。前序业务模型已经办结后，即使其审批模型、智选模型仍在运行，也不改变业务模型已经办结的事实。

“我的办结”以一个模型运行文件为一条记录。点击模型就是查看该模型本身；业务模型详情可显示它触发的审批模型和智选模型，点击关联模型直接查看对应模型运行详情，不再存在独立“模型簇进度”页面。

## 4. API 变化

`GET /api/dashboard` 在原有 `todos`、`done` 基础上增加：

- `completed`：本人相关的已归档模型运行文件；
- `metrics`：今日办结、数字化工作记录、已办理任务、排名及排名参与人数。

`done` 现在严格返回本人已完成的办理记录，不再混入业务模型簇伪记录。

## 5. 数据库与 migration

本版不修改数据库结构，不新增 migration。审批判断和驾驶舱统计复用既有数字化库、模型运行、待办数据及 014～017 已有结构。

## 6. 兼容性

- 历史模型运行记录继续保留；
- 历史已办数据仍从 `todos` 查看；
- 历史已归档模型直接进入“我的办结”；
- V17.2/V17.2.1 关于“已办承载模型簇”的旧界面语义由 V17.3 新规则取代，但对应版本文档保留用于历史追溯。
