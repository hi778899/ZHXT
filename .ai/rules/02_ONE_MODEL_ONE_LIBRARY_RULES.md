# 02 一模型一数字化库规则

## 1. 定义

- 模型：功能执行、运算、判断和结果生成的基本单元。
- 数字化编码：模型及数字化对象的唯一性依据。系统业务规则中不存在“模型 ID”这一身份口径。
- 模型文件名：模型每次运行完成后形成的运行记录名称，是一次模型运行记录的识别与上下游传递依据。
- 数字化库：与一个模型唯一对应，用于保存该模型有效运行结果的存储单元。

## 2. 强制关系

`1 个模型 = 1 个数字化编码 = 1 个对应数字化库`

一个模型可以读取多个其他模型的数字化库，但只能把本模型运行结果写入本模型对应的数字化库。数字化配置、人员、组织、审批层级、会议类型等数据也都存放在相应模型的数字化库中，不另设其他“库”概念。

数字化编码是模型唯一性依据，不得再增加 `model_id`、模型 ID、UUID 等另一套业务身份体系与数字化编码并行。

## 3. 写入边界

允许：

`模型 A → 写入模型 A 对应数字化库`

允许：

`模型 A ← 读取模型 B 数字化库 / 模型 C 数字化库`

禁止：

`模型 A → 直接修改模型 B 对应数字化库中的业务结果`

跨模型业务变化必须通过启动对应模型完成，而不是越权写库。

## 4. 入库语义

- 入库表示模型一次有效运行结果已经形成。
- 未形成有效结果的数据不得伪装为正式入库记录。
- 模型中间运算变量不等于数字化库正式记录。
- 模型每次运行完成必须生成一个模型文件名，并以该文件名标识本次运行记录。
- 同一模型不同次运行必须形成不同模型文件名；不得使用“模型 ID + 实例 ID”替代文件名机制。
- 每条运行记录必须保留数字化编码、模型版本、模型文件名、时间、操作者/触发者和来源链路。

## 5. 模型文件名与链路

模型簇跨模型传递上下文时，统一传递“上一步模型文件名”，并结合数字化编码、数字化标识读取对应运行记录，不依赖页面临时状态，也不使用实例 ID 作为业务链路依据。

统一规则：

- 业务模型完成后生成“业务模型文件名”，审批模型接收该文件名；
- 审批模型完成后生成“审批模型文件名”，智选模型接收该文件名；
- 智选模型根据审批模型文件名追溯审批结果、来源业务模型文件名和相关数字化标识；
- 后续关联模型启动后，再生成自己的模型文件名并继续向下传递；
- 任何需要追溯上一环节的模型，都应保存其来源模型文件名。

模型文件名是“运行记录”的名称，不等于模型唯一性；模型本身的唯一性始终由数字化编码确定。

## 6. 数字化库最低运行记录内容

每条正式运行结果至少应能够追溯：

- 模型数字化编码
- 模型版本
- 本次模型文件名
- 来源模型文件名（无来源时可为空）
- 创建时间
- 操作者或触发者
- 触发方式
- 数字化标识集合
- 与本次业务有关的数字化编码/对象编码
- 有效状态
- 审计信息

具体业务字段由模型定义决定。

## 7. 三类标识不得混用

必须严格区分：

1. **数字化编码**：确定模型或数字化对象的唯一性；
2. **模型文件名**：确定某一次模型运行记录并承担模型簇上下游传递；
3. **数字化标识**：表达该次运行形成的结果、状态或关联触发条件。

不得把数字化标识当模型主键，不得把模型文件名当模型数字化编码，也不得新增模型 ID/实例 ID 替代上述机制。

## 8. 删除与修改

原则上不直接物理覆盖历史运行结果。需要变更时优先采用：

- 重新运行并形成新的模型文件名；
- 新模型版本；
- 状态变更；
- 更正记录；
- 业务允许的撤销/作废流程。

## 9. V17.7.11 既有数字化库文件名统一

数字化库中的既有正式运行记录同样执行当前模型文件名规则，不允许仅新记录使用新格式。升级迁移时，本次模型文件名和来源模型文件名必须与对应运行记录同步更新；同一次运行在 `model_runs`、本模型数字化库、来源/下游模型数字化库引用、待办已办办结中的文件名必须一致。

该迁移属于运行身份字段标准化，不属于修改历史业务结果。迁移可保留原模型文件名审计字段，但旧文件名不得继续用于模型簇触发和业务查询主链路。

## 10. V17.7.13 数字化库“文件记录”统一要求

数字化库中的每一条记录均按“文件记录”管理，必须具有标准模型文件名。`digital_library_records.file_name` 是该库记录的正式文件名字段。

- 真实模型运行记录：与对应 `model_runs.file_name` 一致；
- 历史初始化/系统同步记录：升级时按所属模型、迁移运行人员和原创建时间形成标准文件名；
- 页面不得以 `record_id`、`src0622-*` 等数据库技术键替代文件名；
- 新增数字化库数据必须同步形成标准文件名。

## 11. V17.7.14 “模型运行 → 数字化库”强制形成规则

每一条正式数字化库记录必须由其归属的数据产生模型一次真实运行形成：

`数据产生模型 → model_runs → 本次模型文件名 → digital_library_records(run_id, file_name)`

- `digital_library_records.run_id` 对正式记录不得为空；
- `digital_library_records.file_name` 必须与该 `run_id` 对应的 `model_runs.file_name` 完全一致；
- 系统初始化数据形成 `trigger_mode=system_initialization` 的模型运行；
- 系统源数据后续同步/变更形成 `trigger_mode=system_sync` 的新模型运行；
- seed、migration、账号同步、组织同步等不得绕开数据产生模型直接制造无运行来源的正式库记录；
- 历史 `std-*`、`src0622-*`、`auto0622-*` 仅作为 `legacy_record_id` 保留审计，不得展示为文件名。

`migration_pending` 仅允许历史升级迁移临时使用；生产正常写入、seed 和 sync 代码不得主动生成该状态。待对应数据产生模型及当前数字化编码具备后，必须完成真实模型运行物化后才能作为正式可用记录。
