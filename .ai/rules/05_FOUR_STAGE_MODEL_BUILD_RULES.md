# 05 四阶段模型建设规则——四个建设模型

## 1. 总体目标

模型建设不是代码生成向导，而是系统内可持续维护的模型生产机制。用户应能够通过四个阶段完成模型创建、修改、校验和发布，并最终得到：

- 一个可运行模型；
- 一个与该模型唯一对应的数字化库；
- 完整数字化配置；
- 所需数字化库数据源关联；
- 审批模型关联；
- 智选模型关联；
- 触发配置；
- 可追溯版本。

四个建设模型依次为：

`业务定义模型 → 数字化定义模型 → 模型设计模型 → 模型发布模型`

四阶段建设过程中，目标模型在第一阶段即确定其数字化编码；该数字化编码贯穿后续数字化定义、模型设计、模型发布，作为目标模型的唯一性依据。各建设模型每次运行则生成各自的模型文件名，用于四阶段建设记录和审批、智选链路追溯。

四个建设模型自身都属于正式模型，都必须各自对应一个数字化库，并分别通过模型簇完成阶段确认：

`本阶段建设模型 → 审批模型 → 智选模型 → 下一阶段建设模型`

其中：

- 本阶段建设模型形成有效建设结果并写入本阶段模型对应数字化库；
- 本阶段建设结果正式写入本阶段建设模型对应数字化库后，由该数字化库按硬性链接规则触发审批模型，并传递本阶段建设模型文件名；
- 审批结果正式写入审批模型对应数字化库后，由该数字化库按硬性链接规则触发智选模型，并传递审批模型文件名；
- 智选模型依据数字化标识和配置决定是否进入下一阶段建设模型；
- 第四阶段模型发布模型完成模型簇后，形成并注册目标可运行模型及目标模型对应数字化库。

因此，“完成四阶段”必须意味着四个建设模型均已按模型簇走完，不得仅以四个前端步骤均点击保存作为完成条件。

## 2. 第一阶段：业务定义模型

### 2.1 目标

定义模型“做什么”，而不是先画界面。

### 2.2 至少配置

- 模型名称
- 模型数字化编码
- 模型类别
- 业务目标
- 适用范围
- 发起主体/使用角色
- 输入业务对象
- 输出业务结果
- 启动方式
- 是否进入审批
- 与其他模型的业务关系
- 对应数字化库基本信息

### 2.3 输出

形成可供第二阶段使用的业务定义版本，不直接作为正式运行模型发布。

## 3. 第二阶段：数字化定义模型

### 3.1 目标

把第一阶段业务语义转化为可计算、可存储、可关联的数据定义。

### 3.2 至少配置

- 编码
- 属性
- 标识
- 字段与数字化属性映射
- 标识生成规则
- 数字化库存储规则
- 外部数字化库来源
- 数据校验规则
- 模型关联关系
- 审批输入/输出映射
- 智选输入/输出映射

### 3.3 强制规则

凡字段需要从既有数据中选择，必须绑定相应模型的数字化库，不得在此阶段录入永久静态枚举来替代数字化库数据源。

## 4. 第三阶段：模型设计模型

### 4.1 目标

把业务和数字化定义组装为可执行模型。

### 4.2 至少配置

- 输入界面
- 运算/规则
- 输出界面
- 存储映射
- 表单字段与布局
- 数据源
- 校验器
- 计算规则
- 权限规则
- 审批接口
- 智选接口
- 人工启动 / 智选判断触发 / 定时定量启动 / 数字化库硬性链接触发方式
- 运行成功与失败处理

### 4.3 设计器要求

模型设计器必须真实可操作；组件属性、数据源、规则、存储映射均可保存和再次编辑。禁止出现“看起来像设计器、实际只能通过改代码生效”的实现。

## 5. 第四阶段：模型发布模型

### 5.1 发布前自动校验

至少检查：

- 一模型一数字化库是否成立
- 必填业务定义是否完整
- 数字化定义是否完整
- 字段数据源是否可解析
- 所引用数字化库是否存在且可访问
- 审批配置是否可计算
- 智选关联是否有效
- 运行入口是否存在
- 存储映射是否完整
- 权限是否配置
- 是否存在循环依赖或无终点关联

### 5.2 发布结果

成功发布后，系统必须实际生成/注册：

1. 可运行的模型版本；
2. 对应数字化库结构或逻辑库定义；
3. 模型运行元数据；
4. 审批模型衔接配置；
5. 智选模型衔接配置；
6. 数据源解析配置；
7. 权限和菜单/可发起入口（如适用）；
8. 审计和运行日志能力。

仅保存一份 JSON 草稿不得视为“模型已发布”。

## 6. 四阶段修改规则

已发布模型需要修改时：

- 从已发布版本创建新草稿版本；
- 可回到任一阶段调整；
- 不直接修改历史已发布版本；
- 重新完成校验和发布；
- 新版本生效后保留旧版本运行记录；
- 已经开始的旧运行记录原则上按启动时模型版本继续执行，并继续使用其模型文件名完成后续链路。

## 7. 四个建设模型与模型簇的关系

四阶段建设本身由四个建设模型连续运行，每一个建设模型都必须完成自己的模型簇：

`业务定义模型 → 审批 → 智选 → 数字化定义模型`

`数字化定义模型 → 审批 → 智选 → 模型设计模型`

`模型设计模型 → 审批 → 智选 → 模型发布模型`

`模型发布模型 → 审批 → 智选 → 目标模型注册/生效`

目标模型发布后，其实际业务运行仍继续遵循系统统一模型簇：

`目标业务模型 → 审批模型 → 智选模型 → 关联后续模型`

如果四个建设模型没有逐阶段完成模型簇，或者最终只能保存配置而不能生成可运行目标模型及其对应数字化库，则模型建设不完整。
