# 16 模型数字化编码与模型文件名规则

> 当前有效版本：V17.7.11。数字化对象长度按当前数字化结构执行。本规则对新运行、当前运行中数据及既有数字化库运行记录统一生效。

## 1. 三类身份口径

- 模型唯一性 = 19位模型数字化编码；
- 模型一次运行记录 = 模型文件名；
- 模型运行结果、状态和关联条件 = 当前正式数字化标识。

数字化编码、模型文件名、数字化标识职责固定，不得混用，不得另建模型 ID/实例 ID 作为业务身份或运行链路。

## 2. 当前模型与人员编码

模型数字化编码结构为 `501 + 1 + 001 + 一级业务3位 + 二级业务3位 + 三级业务3位 + 四级业务3位`，共19位。

员工数字化编码结构为 `501 + 1 + 002 + 4位顺序码`，共11位，例如 `50110020001`。

审批模型正式模型数字化编码：`5011001099001001001`。
智选模型正式模型数字化编码：`5011001099001001002`。

## 3. 模型文件名统一格式

所有模型运行统一使用：

`模型文件名 = 模型数字化编码 + 发起/运行人员员工数字化编码 + 时间码`

当前系统存储格式统一采用分隔符连接：

`模型数字化编码-员工数字化编码-时间码`

例如：

`5011001099001001001-50110020001-20260928103000`

规则：

1. 第一段必须为本次运行模型的当前正式19位模型数字化编码；
2. 第二段必须为本次发起人或实际运行人员的当前正式11位员工数字化编码；系统自动运行时按运行规则确定责任/运行人员，不得以用户名、姓名或数据库用户 ID 替代；
3. 第三段为本次运行时间码；迁移既有记录时必须使用该次原始运行时间形成时间码，不得使用迁移执行时间伪造历史顺序；
4. 同一模型每次运行必须形成唯一模型文件名；若原始运行时间精度不足造成冲突，必须按统一时间码冲突处理规则扩展时间精度/顺序，保证唯一且可追溯；
5. 中文显示名称可以另行存在，但不得替代真实模型文件名参与入库、触发、审批、智选、审计或上下游关联。

## 4. 全量适用范围

本规则不只适用于新产生的数据。以下数据全部必须统一使用新模型文件名：

- 新发起和新运行的模型；
- 部署升级时仍处于运行中、待办、审批中、智选中等状态的既有模型运行；
- 已经写入各模型数字化库的既有运行记录；
- 业务模型、审批模型、智选模型及其他模型的本次模型文件名；
- 来源模型文件名、前序业务模型文件名、审批对象业务模型文件名、来源审批模型文件名；
- 待办、已办、办结、驾驶舱、运行日志、审计日志中承担业务链路定位作用的模型文件名引用；
- 数字化库触发下一模型时保存的来源文件名与目标运行关联。

不得出现“新数据使用新规则、旧运行/旧数字化库继续使用旧文件名”的双轨状态。

## 5. 既有数据迁移规则

对不符合当前格式的既有模型文件名必须执行一次性、可审计的数据迁移。

迁移顺序：

`旧运行记录 → 解析/映射当前模型数字化编码 → 解析/映射当前员工数字化编码 → 使用原运行时间生成时间码 → 形成新模型文件名 → 更新本次运行记录 → 更新对应数字化库记录 → 更新全部来源/下游引用 → 校验链路`

强制要求：

1. 必须建立 `旧模型文件名 → 新模型文件名` 的一一映射表/迁移审计记录；
2. 旧文件名可保留在 `原模型文件名/legacy_file_name` 等审计字段中用于追溯，但不得继续作为当前业务链路键；
3. 若旧记录缺少19位模型数字化编码或11位员工数字化编码，必须先通过正式数字化配置完成映射；不得自行拼接、猜测或使用旧16位编码继续生成“新文件名”；
4. 若无法形成唯一合法映射，该记录必须进入迁移异常清单并阻止该记录继续跨模型流转，直到配置补齐；
5. 迁移不得修改业务内容、审批结论、智选结论、办理时间等业务事实，只修改模型文件名及其关联引用；
6. 迁移必须在同一数据一致性边界内完成，禁止只更新 `model_runs` 而不更新数字化库或上下游来源文件名。

## 6. 模型簇文件名传递

模型簇统一按：

`业务模型文件名 → 审批模型 → 审批模型文件名 → 智选模型 → 后续关联模型`

上下游只传递当前新规则生成的真实模型文件名。部署迁移完成后，不允许以旧格式文件名继续新增来源关联。

## 7. 数字化库中的文件名要求

每条模型运行正式入库记录必须保存：

- 当前新规则的本次模型文件名；
- 当前新规则的来源模型文件名（无来源时为空）；
- 对应模型数字化编码；
- 对应发起/运行人员员工数字化编码；
- 原始运行时间/时间码；
- 如由旧数据迁移而来，可附加原模型文件名作为审计字段。

数字化库、运行记录、待办已办办结和模型簇关联中的同一次运行必须引用同一个新模型文件名。

## 8. 禁止事项

- 禁止保留旧文件名作为现行业务主链路并仅对新运行使用新规则；
- 禁止只修改页面显示名称而不修改真实运行/数字化库文件名；
- 禁止只更新本次模型文件名而遗漏来源模型文件名和下游引用；
- 禁止使用迁移时间替代原运行时间生成历史记录时间码；
- 禁止以姓名、用户名、用户表 ID、模型 ID、run_id 或实例 ID 替代数字化编码组成模型文件名；
- 禁止让同一模型的两次运行复用同一个模型文件名。

## 9. 代码与数据库落地要求

1. 运行时文件名生成函数必须拒绝历史16位模型编码和历史16位员工编码；历史值只允许迁移/审计读取；
2. 数据库升级必须建立员工编码迁移审计、模型文件名旧→新迁移审计及异常清单；
3. 同一次迁移必须原子更新 `model_runs`、对应数字化库记录、待办/已办/办结承载内容、审批/智选输入输出、触发失败记录和审计元数据中的旧文件名引用；
4. `model_runs.file_name` 对新写入数据必须受当前格式约束，当前格式文件名必须唯一；
5. 仍处于运行中但无法完成合法文件名映射的记录必须进入迁移异常清单，并禁止继续办理或跨模型触发，不得继续生成旧格式下游数据；
6. 同一秒内发生同模型同人员重复运行时，时间码允许追加毫秒/顺序码扩展，但模型数字化编码、员工数字化编码两段不得变化。

## 10. 验收要求

升级后必须能够证明：

1. 新运行100%符合新文件名格式；
2. 迁移范围内既有运行记录100%具有新文件名；
3. 各数字化库中的模型文件名与对应运行记录一致；
4. 来源模型文件名能够沿业务→审批→智选→后续模型完整追溯；
5. 待办、已办、办结、驾驶舱点击均能通过新文件名定位同一真实运行；
6. 不存在仍参与现行业务链路的旧格式文件名；
7. 每条被迁移记录均可通过旧→新映射审计追溯。

# 16 模型数字化编码与模型文件名规则

## 1. 核心口径

系统对模型及其运行记录只采用以下业务口径：

1. **模型唯一性 = 数字化编码**；
2. **模型一次运行记录 = 模型文件名**；
3. **模型运行结果、状态、关联触发条件 = 数字化标识**。

三者职责固定，不得混用，不得再建立与之平行的另一套模型唯一性或运行记录识别机制。

## 2. 数字化编码

数字化编码用于确定模型唯一性，并贯穿：

- 四阶段模型建设；
- 模型注册；
- 模型版本；
- 数字化库归属；
- 模型关联配置；
- 审批配置；
- 智选配置；
- 权限配置；
- 模型查询与运行。

同一个模型发布不同版本时，模型数字化编码保持其模型身份语义，版本信息单独记录，不得把版本号另造为模型身份。

## 3. 模型文件名

模型每运行一次，都必须生成本次“模型文件名”。模型文件名代表该次模型运行记录。

模型文件名至少承担：

- 定位本次模型运行记录；
- 读取本次运行输入、输出和数字化标识；
- 保存来源模型文件名；
- 作为审批模型接收业务模型运行记录的依据；
- 作为智选模型接收审批模型运行记录的依据；
- 作为后续关联模型追溯上一步业务链路的依据；
- 作为审计、故障排查和历史追溯的业务链路字段。

同一模型多次运行必须产生不同模型文件名。

## 4. 模型簇中的文件名传递

模型簇统一按以下方式传递运行记录：

`业务模型文件名 → 审批模型 → 审批模型文件名 → 智选模型 → 后续关联模型`

规则：

- 审批模型接收“业务模型文件名”；
- 审批模型通过该文件名读取业务模型对应数字化库中的正式运行记录；
- 审批完成后生成“审批模型文件名”；
- 智选模型接收“审批模型文件名”；
- 智选通过审批模型文件名追溯审批结果及来源业务模型文件名；
- 智选触发后续模型时，应把必要的来源文件名关系继续传递；
- 后续模型每次实际运行仍生成自己的模型文件名。

## 5. 四阶段模型建设中的使用

四阶段目标模型的唯一性从业务定义阶段开始即由数字化编码确定：

`业务定义模型 → 数字化定义模型 → 模型设计模型 → 模型发布模型`

四个建设模型自身每次运行均生成各自模型文件名，并按照：

`建设模型文件名 → 审批 → 审批模型文件名 → 智选 → 下一建设模型`

完成全链路流转。

模型发布完成后，应形成：

- 目标模型数字化编码；
- 目标模型可运行版本；
- 目标模型对应数字化库；
- 目标模型的模型簇配置；
- 目标模型运行时的模型文件名生成与传递规则。

## 6. 数字化库触发模型规则

模型簇的硬性衔接必须由数字化库触发，不得把“硬性触发”写成没有主体的抽象动作。

运行顺序必须是：

`模型运行 → 生成本次模型文件名 → 正式结果写入本模型对应数字化库 → 数字化库依据触发配置启动下一模型 → 传递上一环节模型文件名`

在业务模型簇中至少遵循：

- 业务模型对应数字化库有效入库后，触发审批模型；
- 审批模型对应数字化库有效入库后，触发智选模型；
- 智选模型根据数字化标识、数据条数和关联配置决定后续模型运行；其后续关联启动按智选规则执行，不得与数字化库硬性链接概念混淆。

数字化库触发模型时，必须以已正式入库的模型文件名运行记录作为触发来源，并保存触发来源、目标模型数字化编码和触发结果，保证链路可追溯。

不得采用以下实现：

- 上一步模型在尚未完成数字化库正式入库前直接调用下一模型；
- 前端保存成功事件代替数字化库触发；
- 仅写“硬性触发”但不明确是哪个数字化库、基于哪条模型文件名运行记录触发；
- 数字化库已经入库，但另由独立业务代码重复决定是否启动审批或智选。

## 7. 数据存储最低要求

模型定义至少能够以数字化编码检索。

模型运行记录至少保存：

- 模型数字化编码；
- 模型版本；
- 本次模型文件名；
- 来源模型文件名；
- 运行时间；
- 操作者或触发者；
- 触发方式；
- 输入/输出必要内容；
- 数字化标识；
- 有效状态；
- 审计信息。

## 8. 开发红线

- 不得以数据库自动生成键替代数字化编码作为模型业务身份；
- 不得以运行序号替代模型文件名作为模型簇链路字段；
- 不得通过页面临时状态串联模型簇；
- 不得只保存“上一步模型名称”而不保存来源模型文件名；
- 不得把数字化标识误作模型唯一性；
- 不得把模型文件名误作模型唯一性；
- 不得让同一模型的两次运行复用同一个模型文件名。
