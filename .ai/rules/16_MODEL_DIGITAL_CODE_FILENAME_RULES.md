# 16 模型数字化编码与模型文件名规则

> 当前有效版本：V17.5。数字化对象长度按《数字化编码与审批标准库0622 - 副本》分别执行。

## 1. 三类身份口径

- 模型唯一性 = 19位模型数字化编码；
- 模型一次运行记录 = 模型文件名；
- 模型运行结果、状态和关联条件 = 19位数字化标识（历史16位仅兼容）。

## 2. 当前模型与人员编码

模型数字化编码结构为 `501 + 1 + 001 + 一级业务3位 + 二级业务3位 + 三级业务3位 + 四级业务3位`，共19位。

员工数字化编码结构为 `501 + 1 + 002 + 4位顺序码`，共11位，例如 `50110020001`。

审批模型正式模型数字化编码：`5011001099001001001`。
智选模型正式模型数字化编码：`5011001099001001002`。

## 3. 模型文件名

模型文件名继续按“模型数字化编码 + 发起/运行人员员工数字化编码 + 时间码”生成并承担一次运行追溯。新运行使用当前19位模型编码与11位员工编码；历史16位文件名保持可读取。

## 4. 模型簇文件名传递

`业务模型文件名 → 审批模型 → 审批模型文件名 → 智选模型 → 后续关联模型`。上下游只传递真实模型文件名，不新增实例ID业务口径。

## 5. 历史兼容

历史16位模型/人员/标识继续允许解析，不批量篡改既有运行文件名。新建模型、人员和数字化标识禁止继续生成16位数据。

# 16 模型数字化编码与模型文件名规则

## 1. 核心口径

系统对模型及其运行记录只采用以下业务口径：

1. **模型唯一性 = 数字化编码**；
2. **模型一次运行记录 = 模型文件名**；
3. **模型运行结果、状态、关联触发条件 = 数字化标识**。

三者职责固定，不得混用，不得再建立与之平行的另一套模型唯一性或运行记录识别机制。

## 2. 数字化编码

数字化编码用于确定模型唯一性，并贯穿：

- 四阶段模型建设；
- 模型注册；
- 模型版本；
- 数字化库归属；
- 模型关联配置；
- 审批配置；
- 智选配置；
- 权限配置；
- 模型查询与运行。

同一个模型发布不同版本时，模型数字化编码保持其模型身份语义，版本信息单独记录，不得把版本号另造为模型身份。

## 3. 模型文件名

模型每运行一次，都必须生成本次“模型文件名”。模型文件名代表该次模型运行记录。

模型文件名至少承担：

- 定位本次模型运行记录；
- 读取本次运行输入、输出和数字化标识；
- 保存来源模型文件名；
- 作为审批模型接收业务模型运行记录的依据；
- 作为智选模型接收审批模型运行记录的依据；
- 作为后续关联模型追溯上一步业务链路的依据；
- 作为审计、故障排查和历史追溯的业务链路字段。

同一模型多次运行必须产生不同模型文件名。

## 4. 模型簇中的文件名传递

模型簇统一按以下方式传递运行记录：

`业务模型文件名 → 审批模型 → 审批模型文件名 → 智选模型 → 后续关联模型`

规则：

- 审批模型接收“业务模型文件名”；
- 审批模型通过该文件名读取业务模型对应数字化库中的正式运行记录；
- 审批完成后生成“审批模型文件名”；
- 智选模型接收“审批模型文件名”；
- 智选通过审批模型文件名追溯审批结果及来源业务模型文件名；
- 智选触发后续模型时，应把必要的来源文件名关系继续传递；
- 后续模型每次实际运行仍生成自己的模型文件名。

## 5. 四阶段模型建设中的使用

四阶段目标模型的唯一性从业务定义阶段开始即由数字化编码确定：

`业务定义模型 → 数字化定义模型 → 模型设计模型 → 模型发布模型`

四个建设模型自身每次运行均生成各自模型文件名，并按照：

`建设模型文件名 → 审批 → 审批模型文件名 → 智选 → 下一建设模型`

完成全链路流转。

模型发布完成后，应形成：

- 目标模型数字化编码；
- 目标模型可运行版本；
- 目标模型对应数字化库；
- 目标模型的模型簇配置；
- 目标模型运行时的模型文件名生成与传递规则。

## 6. 数字化库触发模型规则

模型簇的硬性衔接必须由数字化库触发，不得把“硬性触发”写成没有主体的抽象动作。

运行顺序必须是：

`模型运行 → 生成本次模型文件名 → 正式结果写入本模型对应数字化库 → 数字化库依据触发配置启动下一模型 → 传递上一环节模型文件名`

在业务模型簇中至少遵循：

- 业务模型对应数字化库有效入库后，触发审批模型；
- 审批模型对应数字化库有效入库后，触发智选模型；
- 智选模型根据数字化标识、数据条数和关联配置决定后续模型运行；其后续关联启动按智选规则执行，不得与数字化库硬性链接概念混淆。

数字化库触发模型时，必须以已正式入库的模型文件名运行记录作为触发来源，并保存触发来源、目标模型数字化编码和触发结果，保证链路可追溯。

不得采用以下实现：

- 上一步模型在尚未完成数字化库正式入库前直接调用下一模型；
- 前端保存成功事件代替数字化库触发；
- 仅写“硬性触发”但不明确是哪个数字化库、基于哪条模型文件名运行记录触发；
- 数字化库已经入库，但另由独立业务代码重复决定是否启动审批或智选。

## 7. 数据存储最低要求

模型定义至少能够以数字化编码检索。

模型运行记录至少保存：

- 模型数字化编码；
- 模型版本；
- 本次模型文件名；
- 来源模型文件名；
- 运行时间；
- 操作者或触发者；
- 触发方式；
- 输入/输出必要内容；
- 数字化标识；
- 有效状态；
- 审计信息。

## 8. 开发红线

- 不得以数据库自动生成键替代数字化编码作为模型业务身份；
- 不得以运行序号替代模型文件名作为模型簇链路字段；
- 不得通过页面临时状态串联模型簇；
- 不得只保存“上一步模型名称”而不保存来源模型文件名；
- 不得把数字化标识误作模型唯一性；
- 不得把模型文件名误作模型唯一性；
- 不得让同一模型的两次运行复用同一个模型文件名。
