# 03 模型簇规则——V17.7.8 当前有效增补

## 1. 业务归档到审批的系统硬性链接

`业务模型 → 业务模型数字化库 → 审批模型` 属于系统固定链路。业务模型完成有效运算并正式写入自身数字化库后，运行引擎必须启动通用审批模型。

该链路不得依赖历史项目中的 `relations`、`afterArchiveEnabled`、`nextModelName` 是否存在，也不得因四阶段修改、项目版本升级或用户误删普通关系而失效。配置中的“业务→审批”关系仅作为可见配置快照；运行引擎始终保留系统硬性兜底。

## 2. 审批启动与审批计算顺序

正确顺序固定为：

`业务数字化库正式入库 → 建立审批模型运行实例（启动中） → 读取来源业务数字化库 → 读取审批相关数字化库 → 计算基础审批目标 → 阈值/特殊属性调整 → 最终审批目标 → 审批路径 → 创建首环节审批待办`。

不得先完成审批目标计算再决定是否创建审批模型运行实例。

## 3. 失败不得静默

如果审批模型已经接到硬性触发，但审批目标、人员、时限、路径等数字化库配置不足，应保留审批模型运行实例并标记“运行异常”，记录具体失败原因。业务模型端同时记录“审批触发异常”。

如果业务数字化库已正式入库，但连审批模型运行实例都未形成，则本次业务提交不得按普通成功返回，必须明确提示“业务模型已归档，但审批模型未成功启动”。

## 4. 请休假模型

请休假模型不设置专用审批调用代码。它作为普通业务模型，完成请休假数字化库归档后，由上述系统硬性链接启动同一个通用审批模型。

# 03 模型簇规则——业务模型、审批模型、智选模型

> 当前有效版本：V17.7.3 规则修订
> 本次修订重点：审批模型正式归档后启动智选模型属于模型簇系统硬性链接，不能依赖历史第4阶段关系配置；智选运行和发起人待办必须真实生成。

## 1. 模型簇统一关系

统一关系继续为：

`业务模型 → 业务模型数字化库 → 审批模型 → 审批模型数字化库 → 智选模型 → 后续关联模型`

业务模型、审批模型、智选模型均为独立模型，分别具有自己的模型文件名、数字化库、运行状态和待办/已办/办结记录。

### 1.1 审批归档到智选的系统硬性链接

`审批模型 → 审批模型数字化库 → 智选模型` 属于模型簇系统固定链路。审批模型形成最终结果并完成正式归档后，系统必须在审批数字化库写入成功后立即启动通用智选模型。

该硬性链接不得依赖以下可变配置才能成立：

- 审批模型历史 `relations` 是否存在；
- `afterArchiveEnabled` 是否被旧版本遗漏；
- `nextModelName` 是否仍保存“智选模型”；
- 审批模型是否经历过四阶段修改、版本号是否大于1；
- 用户是否在模型配置界面误删、禁用或修改了该关系。

因此，运行引擎必须把“审批归档 → 智选”作为系统级必执行关系。模型配置中可以显示该关系，但应标记为**系统固定**，不得作为普通关系删除或禁用。

审批最终结果为同意、不同意、退回终止或其他正式终止意见时，均先启动智选模型；是否继续触发后续业务模型，由智选模型按照“先统计、再判断审批结果、先特殊后正常”的规则决定，审批模型不得自行跳过智选。

智选模型成功启动后必须形成真实智选运行实例、真实模型文件名并写入智选模型数字化库；同时向原业务发起人生成智选结果待办/待确认事项。即使没有任何后续关联模型，也必须保留本次智选运行和智选结果待办，不能因为“无后续模型”而不生成智选模型。

## 2. 关联模型状态的唯一事实来源

驾驶舱、我的已办、我的办结、业务模型详情中显示的审批模型/智选模型状态，必须在查询时根据真实运行数据解析，不得使用业务模型办结时保存的旧快照直接判断。

智选模型状态至少按以下事实校验：

1. 是否已经存在来源审批模型文件名对应的智选模型运行记录；
2. 是否已经生成真实智选模型文件名；
3. 是否已经产生智选模型待办；
4. 是否已经形成智选模型已办/办结；
5. 是否已经写入智选模型数字化库。

只要上述任一运行事实已经证明智选模型被启动，就**禁止显示“未启动”**。

### 2.1 状态判定优先级

同一审批模型对应智选模型时，状态按当前真实数据收敛：

- 已存在智选模型办结/数字化库正式结果 → `已完成`；
- 已存在智选模型运行记录或待办 → `已启动/运行中`；
- 已存在硬性触发记录但运行记录尚在创建 → `启动中`；
- 以上均不存在 → 才允许显示 `未启动`。

“未启动”是排除性状态，不得仅因为业务模型旧记录中没有智选文件名就判定未启动。

## 3. 文件名追溯

关联查询必须沿真实模型文件名执行：

`业务模型文件名 → 审批模型文件名 → 智选模型文件名`

审批模型归档后，审批数字化库触发智选模型时，应保存审批模型文件名作为智选来源。驾驶舱查询智选状态时，应优先通过来源审批模型文件名查找最新真实智选运行，而不是读取业务模型早期快照。

## 4. 已办与办结查看的一致性

“我的已办”和“我的办结”必须调用同一套关联模型状态解析规则。

同一个智选模型在“待办”中已经存在时：

- “我的已办”关联模型不得显示“未启动”；
- “我的办结”关联模型不得显示“未启动”；
- 业务模型详情不得显示“未启动”。

不同页面不得各自维护独立状态字符串。

## 5. 申请阶段、有效阶段

业务模型阶段继续保持：

- 业务模型完成入库、审批尚未形成允许生效的最终结果 → `申请阶段`；
- 审批形成允许业务生效的最终结果 → `有效阶段`；
- 审批不同意/终止 → `审批终止/未生效`。

阶段状态与智选模型是否已启动是两个维度，不得互相替代。

## 6. 验收

至少验证：

1. 审批模型归档后由审批数字化库触发智选；
2. 智选模型一旦生成待办，“我的已办”立即显示智选已启动/运行中；
3. 刷新页面后状态仍一致；
4. 已办、办结、业务详情对同一智选模型显示相同真实状态；
5. 智选完成后状态统一切换为已完成；
6. 只有不存在任何智选运行/待办/触发事实时才显示未启动；
7. 删除或禁用历史审批模型配置中的“审批→智选”关系后，新审批归档仍必须真实启动智选；
8. 审批归档后原业务发起人的“我的待办”必须出现本次智选结果事项；
9. 无后续关联模型时仍必须生成智选运行、智选模型文件名和智选结果待办。

# 03 模型簇规则——业务模型、审批模型、智选模型

> 当前有效版本：V17.4 规则修订
> 修订重点：恢复“申请阶段/有效阶段”查看关系；已办、办结均可沿业务模型展开查看审批模型与智选模型；关联模型点击后直接查看该模型本身。

## 1. 模型簇的统一关系

需要治理审批与后续关联运行的业务统一采用：

`业务模型 → 业务模型数字化库 → 审批模型 → 审批模型数字化库 → 智选模型 → 后续关联模型`

模型簇只是多个独立模型的关联运行关系。业务模型、审批模型、智选模型均保持独立模型、独立模型文件名、独立数字化库、独立运行状态。不得把模型簇做成一个替代各模型详情的“进度模型”或“进度页面”。

## 2. 模型文件名与关联追溯

- 模型唯一性：使用模型数字化编码。
- 一次运行记录：使用本次模型文件名。
- 上下游关联：下一模型保存上一模型文件名；同时保留来源业务模型文件名，使整条模型簇可以反向追溯。
- 查看关联模型时，必须定位到具体模型文件名并打开该模型本身，不得只显示抽象进度。

## 3. 业务模型阶段状态

### 3.1 申请阶段

业务模型已完成并正式写入本业务模型数字化库，数字化库已经启动审批模型，但审批模型尚未形成允许业务生效的最终审批结果时，业务模型处于“申请阶段”。

申请阶段必须能够看到：

- 业务模型文件名；
- 业务模型自身详情；
- 已启动的审批模型文件名及真实状态；
- 审批模型尚未完成时的当前办理状态；
- 已启动的智选模型（如有）及真实状态。

### 3.2 有效阶段

审批模型完成并形成允许该业务生效的审批结果后，业务模型进入“有效阶段”。

有效阶段仍保留完整模型簇关联，可继续查看本次审批模型、智选模型及后续关联模型。

审批不同意或规则明确终止时，不得把业务模型标记为“有效阶段”；应显示真实的审批终止/未生效结果，并保留业务模型与审批模型的关联记录。

## 4. 我的已办查看规则

“我的已办”首先表示本人已经完成过办理动作，但查看时必须保留模型簇追溯能力。

- 如果已办记录属于业务模型：可展开该业务模型关联的审批模型、智选模型。
- 如果已办记录属于审批模型环节：点击该记录直接打开对应审批模型本身，并定位本人的办理记录。
- 如果已办记录属于智选模型：点击直接打开对应智选模型本身。
- 业务模型展开后，审批模型、智选模型必须显示真实模型文件名和真实运行状态。
- 点击“审批模型”或“智选模型”必须进入对应模型详情，不得进入另一套模型簇进度界面。

## 5. 我的办结查看规则

“我的办结”以单个已经完成的模型运行文件为记录颗粒，但业务模型办结记录仍承担模型簇根节点的追溯入口。

- 业务模型自身完成后即可进入办结，不因审批/智选尚未完成而撤销业务模型的办结事实。
- 业务模型办结详情必须同时显示其当前阶段：申请阶段、有效阶段或审批终止/未生效。
- 业务模型办结详情必须能展开关联审批模型、智选模型。
- 审批模型完成后，审批模型自身也进入办结；点击审批模型必须打开审批模型本身。
- 智选模型完成后，智选模型自身也进入办结；点击智选模型必须打开智选模型本身。

## 6. 数字化库硬性链接触发

业务模型、审批模型、智选模型之间仍采用数字化库正式入库后的硬性链接触发：

`业务模型运行 → 业务模型数字化库入库 → 触发审批模型`

`审批模型运行 → 审批模型数字化库入库 → 触发智选模型`

页面展开和查看不得改变此运行机制。前端只读取真实运行关系，不负责伪造或推进模型状态。

## 7. 验收要求

至少验证：

1. 业务模型入库后显示“申请阶段”；
2. 申请阶段可以展开并打开真实审批模型；
3. 审批完成并允许生效后业务模型显示“有效阶段”；
4. 已办中能从业务模型展开审批/智选，也能直接打开本人办理过的审批模型；
5. 办结中业务模型、审批模型、智选模型均可查看各自模型详情；
6. 不再使用一个独立“模型簇进度页面”替代真实模型详情。

# 03 模型簇规则——业务模型、审批模型、智选模型

## 1. 统一模型簇

对需要治理审批与后续关联运行的业务，统一采用：

`业务模型 → 审批模型 → 智选模型 → 后续关联模型`

模型簇是一组按数字化关系协同运行的模型，不是把所有逻辑塞进一个模型。

模型簇中统一遵循：模型本身用数字化编码确定唯一性；每一次模型运行用该次生成的模型文件名识别。上一步模型完成后，将其模型文件名传递给下一模型，下一模型据此查询上一环节正式运行记录。


## 2. 业务模型

职责：

- 承担具体业务操作与运算；
- 读取业务所需的其他模型数字化库；
- 形成业务有效结果；
- 生成业务数字化标识；
- 将结果写入本业务模型数字化库；
- 业务结果正式写入本业务模型对应数字化库后，由该数字化库按硬性链接规则触发审批模型，并将业务模型文件名传入审批模型。

业务模型不得自行复制一套审批流程或自行决定所有后续模型。

## 3. 审批模型

职责：

- 接收业务模型文件名，并据此读取对应业务运行记录；
- 根据审批层级、人员、阈值、会签及其他审批规则动态生成审批路径；
- 记录审批过程与最终/阶段结果；
- 结果写入审批模型自己的数字化库；
- 审批结果正式写入审批模型对应数字化库后，由该数字化库按硬性链接规则触发智选模型，并将审批模型文件名传入智选模型。

审批模型应尽量通用化。审批层级、人员、阈值、时限等规则配置必须来自相应模型的数字化库，不为每个业务复制独立审批代码。

## 4. 智选模型

职责：

- 接收审批模型文件名，并据此读取审批运行记录及其来源业务模型文件名；
- 读取审批结果、来源业务标识及数字化关联配置；
- 先处理特殊规则，再处理正常关联规则；
- 计算需要处理的数字化标识集合；
- 筛选存在模型关联的标识集合；
- 对每个关联标识按有效数据条数逐条触发相应模型运行；每次运行生成新的模型文件名；
- 记录智选结果到本智选模型数字化库。

审批不同意时，按照规则提醒/终止，不得继续触发正常后续业务模型。

## 5. 数字化库硬性链接触发

“硬性链接”必须理解为**数字化库触发模型**，触发主体不是上一步模型本身，也不是前端页面按钮。模型先完成运行并形成模型文件名，再把正式结果写入本模型对应数字化库；数字化库确认有效入库后，依据预先配置的硬性链接启动下一模型。

统一链路为：

`业务模型运行 → 业务模型对应数字化库正式入库 → 数字化库触发审批模型`

`审批模型运行 → 审批模型对应数字化库正式入库 → 数字化库触发智选模型`

触发时必须携带上一环节模型文件名，使下一模型能够从对应数字化库准确读取该次正式运行记录。

以下链接属于平台级强制约束，不依赖用户是否记得手工点击：

- 业务模型对应数字化库有效入库 → 触发审批模型；
- 审批模型对应数字化库有效入库 → 触发智选模型。

不得实现为“业务模型代码直接调用审批模型”或“审批模型代码直接调用智选模型”。模型与模型之间的硬性衔接必须以数字化库正式入库事件为边界。

若某业务明确无需审批，应通过正式配置表达特殊路径，不得通过删除数字化库触发规则或在业务代码中绕开模型簇实现。

## 6. 启动方式

系统统一支持并由模型配置明确：

1. 人工点击启动
2. 智选判断触发
3. 定时/定量启动
4. 数字化库硬性链接触发

## 7. 多标识多数据触发

智选必须支持一条模型运行记录内包含多个数字化标识、每个标识又对应多条有效数据的情况。应按“标识 → 数据条数 → 展开待触发运行”的顺序生成触发集合，不得简单用一个布尔值代替。

## 8. 可追溯性

模型簇中的每次模型运行都必须通过模型文件名追溯上一步来源和下一步触发结果，形成完整链路。
