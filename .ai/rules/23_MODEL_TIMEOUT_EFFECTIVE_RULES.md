# V17.7.22 模型时限配置生效与读取规则

> 当前有效版本：V17.7.22

## 1. 唯一正式数据源

审批模型的规定时限唯一读取 `模型时限数字化库（lib-standard-model-timeout）`。前端、审批待办、业务模型代码、审批模型输出快照均不得把固定 `8` 作为正式规定时限。

模型时限模型字段与数字化标识对应关系固定为：

- `模型时限（小时） / timeoutHours` → `5013001001110171`
- `适用业务范围 / businessDomains` → `5013001001110172`

运行时必须同时兼容数字化库正式 `identifier_values` 与历史0622中文字段，但优先读取数字化标识值。

## 2. 审批后生效

人工发起模型时限模型后，其模型运行可以先形成对应数字化库记录用于模型簇追溯，但在其审批模型尚未归档同意前，该记录状态为 `待审批`，不得成为其他审批模型的正式时限来源。

正式生效链固定为：

`模型时限模型运行 → 模型时限数字化库候选记录 → 审批模型完整 Path_final → 审批结果同意并归档 → 该时限配置生效 → 后续新审批运行读取新值`

审批结果为不同意、退回修改或其他终止结果时，该时限配置不得生效。

## 3. 当前有效值选择

同一来源业务可能命中多条时限配置时，统一按以下顺序收敛为一个当前有效值：

1. 业务范围匹配越具体越优先；
2. 业务层级匹配越深越优先；
3. 同等匹配精度下，人工模型运行且已经审批生效的配置优先于系统同步/初始化基线；
4. 同类人工配置再次修改时，以最新审批生效时间为当前有效配置。

系统初始化的 `8` 仅是基线配置，不得永久覆盖后来已经审批生效的模型时限配置。

## 4. 运行快照边界

规定时限在审批模型首次形成 `Path_final` 时写入本次审批节点运行快照。已经启动或正在办理的审批实例保持当次快照，不因后续模型时限配置变化而反向改写。

新的模型时限配置审批生效后，后续新启动的审批模型必须读取最新当前有效值。

## 5. 数字化库规范化

模型时限模型审批同意归档时，应将数字化标识值同步规范化为数字化库可直接核查的正式字段：

- `模型时限`
- `业务领域集合`
- `数据版本 = 0622`
- `配置状态 = 生效`
- `审批结果`
- `审批完成时间`
- `生效时间`

历史人工运行记录在数据库迁移时按其实际审批结果补齐上述状态，不得通过人为固定值覆盖用户已经审批通过的配置。

## 6. 验收

至少验证：

1. 人工提交某业务范围的新时限，例如由 `8` 修改为其他值；
2. 新配置审批完成前，新发起审批仍不得读取未批准值；
3. 新配置审批同意归档后，再发起一条适用该业务范围的新业务；
4. 新审批模型的 `规定时限` 必须等于新审批生效值，而不是初始化 `8`；
5. 同一业务范围再次修改并审批通过后，后续新审批读取最新生效值；
6. 审批未通过的模型时限记录不得覆盖当前有效值；
7. 既有运行中的审批实例不因时限配置更新而被反向改写。
