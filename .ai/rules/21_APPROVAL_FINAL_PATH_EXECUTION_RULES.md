# 21 最终审批路径执行与归档规则

> 当前有效版本：V17.7.19  
> 适用于所有进入通用审批模型的来源模型。


## 0. V17.7.19 代码执行硬约束

- `Path_final` 必须在审批模型首次形成路径时固化为本次运行的必经节点快照，后续办理不得因某一子路径完成而缩短。
- 每次节点办理完成后，运行引擎必须按本次审批运行已经完成的 `step_index` 集合重新查找 `Path_final` 中下一未完成必经节点。
- 只要仍存在下一未完成必经节点，就必须保持审批模型“审批中/办理中”并创建下一节点待办。
- 正常“同意”归档前必须再次校验：`已完成必经节点数 = Path_final 必经节点总数`。不满足时必须拒绝归档。
- 技术/业务审查节点必须由审批分管配置数字化库 + 员工信息数字化库直接形成；不得从一个审查人员自动追加行政负责人作为审查节点。
- 员工请休假中“考勤主管”必须通过考勤管理业务属性与“业务审核岗”技术/业务审查分管配置形成，不得写死人员姓名。

## 1. 唯一完成判定对象

审批模型的正常完成判定对象只能是最终审批路径 `Path_final`。

`Path_final = Merge(Path_approval, Path_technical_review, Path_business_review, 路径配置) → 按实际人员去重 → 正式办理路径`

`A_final`、`T_final`、`B_final` 以及任一子路径是否完成，只用于路径生成和内部状态判断，不得直接触发审批模型归档。

## 2. 正常同意流

当前节点同意后：

1. 标记当前 `Path_final` 节点完成；
2. 查找 `Path_final` 中下一未完成必经节点；
3. 若存在下一节点，审批模型继续保持“办理中”，并向下一实际人员产生待办；
4. 若不存在下一节点，才形成最终同意结果并归档。

## 3. 请休假验收基准

员工请休假标准示例：

`员工发起 → 部门经理审批 → 考勤主管业务审查 → 审批模型归档 → 智选模型`

部门经理同意后：

- 行政审批子路径可以视为完成；
- 但 `Path_final` 尚有“考勤主管”节点；
- 审批模型必须继续处于办理中；
- 必须产生考勤主管待办；
- 不得归档；
- 不得提前触发智选。

考勤主管完成后：

- `Path_final` 全部必经节点完成；
- 审批模型形成最终结果并归档；
- 审批模型数字化库正式入库；
- 系统硬性触发智选模型。

## 4. 终止流

若当前节点选择的审批意见在正式数字化配置中被标记为“终止”：

- 可以不再执行剩余 `Path_final` 节点；
- 必须保存终止节点、终止意见、未执行节点集合；
- 形成正式终止审批结果并归档；
- 归档后仍必须触发智选模型；
- 智选读取终止结果决定后续不启动正常关联或执行特殊逻辑。

## 5. 串联与并联

- 串联：严格按 `Path_final` 顺序逐节点推进。
- 并联：同一并联组全部必经节点完成后，才能进入下一组或归档。
- 任一并联组未完成时，不得因行政审批子路径已完成而提前归档。

## 6. 归档前硬校验

正常同意结果归档前必须满足：

`Path_final 必经节点总数 = Path_final 已完成必经节点数`

否则归档操作必须拒绝，并记录审批路径完整性异常。

终止结果不执行上述等式要求，但必须存在有效终止配置和终止节点记录。

## 7. 普通界面

本规则只改变执行与完成判定，不改变 V17.7.17 的界面约束：普通审批界面仍只显示最终审批路径 `Path_final`，格式为“岗位/角色名称（员工数字化编码）”。
