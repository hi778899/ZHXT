# 14 构建、部署与运维规则

## 1. 环境

至少区分：

- 开发环境
- 测试/预生产环境
- 正式环境

正式环境不得直接使用开发服务器命令代替生产构建，除非项目架构明确且经过验证。

## 2. 可重复构建

应固定：

- Node/Python 等运行时版本
- 包管理器版本
- lock 文件
- 构建命令
- 环境变量说明
- migration 执行顺序

## 3. 部署顺序

典型发布流程：

`备份 → 拉取版本 → 安装依赖 → migration → build → 启动/滚动更新 → 健康检查 → 冒烟测试 → 发布完成`

具体项目可调整，但必须可重复。

## 4. 健康检查

至少检查：

- Web/API 存活
- 数据库连接
- 核心配置加载
- 模型注册表可读
- 审批/智选关键依赖可用

## 5. 回滚

每个正式版本应能定位到 Git Tag。发布前应明确应用回滚和数据库恢复策略，禁止只保留“最新压缩包”而没有版本定位。

## 6. 日志

至少保留：

- 应用日志
- 错误日志
- 模型运行日志
- 审批日志
- 智选日志
- 审计日志

生产故障必须能够通过模型数字化编码、模型文件名和来源模型文件名串联业务链路；可附加技术追踪信息，但不得以实例 ID 替代模型文件名。

## 7. Node 包仓库与容器构建

- Docker/CI 构建不得把 `registry.npmjs.org` 写死为唯一可用依赖源；必须允许通过环境变量切换官方仓库、镜像仓库或企业内网 npm 私服。
- 使用 Corepack 时，包管理器本体下载地址与项目依赖下载地址必须同步配置，避免只切换 pnpm registry、Corepack 仍访问官方 npm。
- 多阶段 Docker 构建中，生产 runtime 阶段不得再次联网安装与 build 阶段相同的依赖；应复用已验证的生产依赖产物，降低外网依赖与重复下载。
- registry 切换只属于构建基础设施配置，不得改变业务源码、模型运行规则或数据库数据。
