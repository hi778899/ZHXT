# 22 模型数字化配置完整性与基础审批数据规则

> 当前有效版本：V17.7.20

## 1. 适用范围

本规则适用于系统中所有可运行且归档后进入通用审批模型的模型，包括业务模型、基础数字化库模型、审批智选配置模型、模型建设模型和其他已发布模型。

## 2. 模型数字化配置是审批入口的前置条件

1. 每个可运行模型必须在“模型数字化配置数字化库”中存在且仅存在一条当前有效 `数据版本=0622` 配置。
2. 配置至少包含：模型数字化编码、模型名称、数字化属性集合、数字化标识集合、数据版本。
3. 审批模型必须以来源模型数字化编码查该库；不得按中文模型名称猜测业务领域。
4. 模型已发布、可发起但缺少模型数字化配置时，属于配置缺陷，不得通过审批代码写默认业务属性兜底。
5. 发布/seed/初始化应在用户发起前完成该配置；不得等审批失败后才临时拼接。

## 3. 当前基础数字化模型配置

- `请假类型标准模型`，模型数字化编码 `5011001001100003001`：业务分类数字化属性使用“考勤管理” `5012001005001000000`。
- `模型时限模型`，模型数字化编码 `5011001001100022001`：业务分类数字化属性使用“数字化管理” `5012001007000000000`。
- `数字化管理` 必须作为正式业务分类由业务分类模型运行形成，不得只作为代码常量存在。
- 设备管理部承担数字化管理业务归属；相应部门负责人通过审批分管配置参与行政审批。

## 4. 考勤主管业务审查配置完整性

员工请休假及属于考勤管理的基础模型需要业务审查时，必须同时满足：

1. 员工信息数字化库中存在考勤主管的当前11位员工数字化编码；
2. 考勤主管的组织名称数字化属性指向正式组织“组织人事部”；
3. 组织数字化属性为“业务审核岗”；
4. 业务领域包含考勤管理 `5012001005001000000`；
5. 审批分管配置数字化库中“业务审核岗”的技术/业务审查分管包含考勤管理；
6. 上述记录均由对应数据产生模型的真实 `model_runs` 形成，禁止直接制造 `run_id=NULL` 的数字化库记录。

满足后，通用审批引擎根据数字化库计算 `Path_final`，不得在审批代码中写死“考勤主管”姓名。

## 5. 配置变更与同步

系统初始化、默认账号修正、业务归属调整、审批分管调整和模型数字化配置补齐，必须通过对应数据产生模型形成 `system_initialization` 或 `system_sync` 运行，再更新数字化库记录。

历史系统默认“考勤主管/综合管理部”不符合当前0622组织名称数字化库；默认测试配置统一收敛到“组织人事部”。若管理员已明确配置其他正式组织，不得无条件覆盖。

## 6. 启动前校验

可发起模型至少校验：

`当前19位模型数字化编码 → 模型数字化配置数字化库 → 业务分类数字化属性 → 审批分管配置 → 发起人员工信息 → Path_final`

任何前置配置缺失必须明确指出缺少的数字化库数据，不得静默归档或跳过审批。
