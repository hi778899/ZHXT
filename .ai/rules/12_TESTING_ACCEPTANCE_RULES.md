# 12 测试与验收规则

## 1. 测试层级

至少覆盖：

- 单元测试
- API/服务测试
- 数据库 migration 测试
- 模型运行集成测试
- 审批集成测试
- 智选集成测试
- 关键 E2E
- 生产构建验证

## 2. 模型建设核心验收

必须验证：

1. 四阶段均可编辑并持久化；
2. 可从旧版本创建新草稿修改；
3. 发布后产生可运行模型；
4. 发布后建立对应数字化库；
5. 需要选择既有数据的字段能从指定数字化库动态加载；
6. 业务模型运行后正确写入本模型对应数字化库；
7. 入库后自动进入审批；
8. 审批完成后自动进入智选；
9. 智选按标识触发正确后续模型；
10. 全链路可通过“数字化编码 + 模型文件名 + 来源模型文件名”追溯；
11. 系统不得依赖模型 ID/实例 ID 识别模型或串联模型簇。

## 3. 回归测试

修改公共模型引擎、审批、智选、数据源或数字化配置时，必须回归至少一个既有已发布模型，防止平台改动导致历史模型失效。

## 4. 负面测试

必须考虑：

- 所引用数字化库不存在或不可用
- 标识无关联模型
- 审批不同意
- 重复提交
- 权限不足
- 数据源不可用
- migration 失败
- 模型版本不兼容
- 循环触发
- 重复定量触发

## 5. 验收证据

重要需求应保留测试日志、CI 结果、接口结果或界面截图，不能只以“开发人员说能用”作为验收依据。

## V17.7.11 文件名迁移验收

升级验收必须增加：旧格式文件名扫描结果为0（审计映射字段除外）；运行记录与数字化库文件名一致率100%；来源文件名无孤儿引用；业务→审批→智选链路能够使用新文件名完整追溯；待办、已办、办结和驾驶舱能够打开迁移后的既有记录；重复/冲突文件名为0。

## V17.7.14 数字化库模型运行来源验收

升级验收增加以下硬指标：

1. 正式数字化库记录 `run_id` 非空率为 100%（仅明确列入迁移异常且标记 `migration_pending` 的历史问题记录除外）；
2. 每个 `run_id` 均能关联真实 `model_runs`；
3. 数字化库 `file_name` 与对应 `model_runs.file_name` 一致率 100%；
4. 业务定义、员工、组织、模型时限、审批分管等基础/配置库同样满足上述要求；
5. 源代码除统一的模型归档/系统运行归档入口外，不得存在直接制造 `run_id=NULL` 正式记录的写库路径；
6. 页面不得出现 `std-*`、`src0622-*`、UUID 等技术键作为“文件名”；
7. 首次安装、旧库升级和系统源数据变更三种场景都要验证 `system_initialization/system_sync` 运行可追溯。
