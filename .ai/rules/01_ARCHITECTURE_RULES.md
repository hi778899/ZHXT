# 01 系统架构规则

## 1. 推荐逻辑分层

系统至少保持以下逻辑边界：

1. 表现层：驾驶舱、模型建设器、业务运行页面、管理后台。
2. 应用层：用例编排、事务边界、权限检查、模型调用。
3. 领域层：模型定义、数字化规则、审批规则、智选规则、触发规则。
4. 引擎层：模型运行、审批、智选、数据源、定时/定量触发。
5. 数据层：模型元数据、数字化库、模型运行记录、日志、审计。
6. 基础设施层：数据库、缓存、文件、消息、配置、构建部署。

## 2. 模块边界

核心模块应独立承担单一职责，禁止形成一个巨型服务同时处理模型设计、审批、智选、权限和存储。

推荐核心域：

- Model Builder
- Model Registry
- Digitalization
- Data Source
- Runtime Engine
- Approval Engine
- Smart Select Engine
- Trigger Engine
- Digital Library / Data Store
- Identity & RBAC
- Audit & Observability

## 3. 配置驱动原则

以下内容优先配置化而非硬编码：

- 表单字段和布局
- 字段数据源
- 校验规则
- 数字化属性与标识
- 审批层级
- 审批人员来源
- 智选关联规则
- 触发方式
- 模型关系
- 发布版本

## 4. 向后兼容

平台升级不得自动改变已发布模型的运行语义。若引擎规则发生不兼容变化，应提供：

- 版本化运行协议；或
- 模型迁移工具；或
- 明确 migration。

## 5. 禁止事项

- 前端直接拼装最终审批路径作为唯一事实来源。
- 将审批、智选规则散落在多个页面组件中。
- 直接通过页面代码修改数据库表结构。
- 用 UI 状态代替正式运行状态。
- 用显示文本、模型 ID 或实例 ID 作为模型唯一性或模型运行链路依据；模型唯一性使用数字化编码，运行记录使用模型文件名。
