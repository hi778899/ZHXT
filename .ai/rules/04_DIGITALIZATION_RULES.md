# 04 数字化规则与配置

> 当前有效版本：V17.5（依据《数字化编码与审批标准库0622 - 副本》）
> 本版取消“所有对象统一16位”的现行口径，改为按数字化对象使用各自正式编码结构。历史16位结构仅用于兼容既有数据，不再作为新建数据规则。

## 1. 数字化三要素

系统继续统一使用“数字化编码、数字化属性、数字化标识”三要素：

- **数字化编码**：确定模型、员工等数字化对象身份与唯一性；
- **数字化属性**：描述业务分类、组织层级、组织名称等可计算属性；
- **数字化标识**：表达业务值、结果、状态及智选关联条件。

模型唯一性使用模型数字化编码；一次模型运行使用模型文件名；数字化标识不得替代模型数字化编码或模型文件名。

## 2. 当前正式编码结构

单位代码统一为 `501`。各对象按下列结构分别编码，不再要求统一位数。

| 数字化对象 | 当前结构 | 当前长度 | 示例 |
|---|---|---:|---|
| 模型数字化编码 | 单位代码 + `1` + `001` + 一级业务编码 + 二级业务编码 + 三级业务编码 + 四级业务编码 | 19位 | `5011001005001001001` |
| 员工数字化编码 | 单位代码 + `1` + `002` + 4位顺序码 | 11位 | `50110020001` |
| 业务分类数字化属性 | 单位代码 + `2` + `001` + 一级业务编码 + 二级业务编码 + 三级业务编码 + 四级业务编码；未到层级以 `000` 补位 | 19位 | `5012001005001001001` |
| 数字化标识 | 单位代码 + `3` + 一级业务编码 + 二级业务编码 + 三级业务编码 + 四级业务编码 + 标识码 | 19位 | `5013001005001001001` |
| 组织数字化属性 | 单位代码 + `2` + `003` + 组织性质码 + 组织层级码 + 内设职级码 | 12位 | `501200302041` |
| 组织名称数字化属性 | 单位代码 + `2` + `004` + 组织性质码 + 组织名称码 | 12位 | `501200402004` |

组织性质码：`01` 党组织、`02` 行政机构、`03` 委员会。阈值类型码：`01` 金额、`02` 人员、`03` 天数。

## 3. 结构约束

1. 新建模型必须使用19位模型数字化编码；新建员工使用11位员工数字化编码；新建数字化标识使用19位标识。
2. 组织数字化属性和组织名称数字化属性均为12位，但二者编码类型段不同，不得混用。
3. 历史16位模型编码、人员编码、数字化标识仅允许兼容读取、历史运行追溯和旧数据迁移；不得作为新建配置的校验标准。
4. 任何代码、界面或数据库约束都不得再次写成“所有数字化对象必须16位”。
5. 文档已给出的编码按原值入库；文档未给出的编码不得由 AI 自行编造。

## 4. 当前基础模型·数字化库

依据0622数据，系统至少配置并可读取以下数字化库：

- 业务分类数字化库；
- 模型数字化配置数字化库；
- 阈值类属数字化库；
- 组织数字化库；
- 组织名称数字化库；
- 业务归属数字化库；
- 组织关系数字化库（沿用既有审批路径资料）；
- 审批分管配置数字化库；
- 员工数字化库；
- 员工信息数字化库；
- 模型时限数字化库；
- 标识关联配置数字化库；
- 审批模型数字化库；
- 智选模型数字化库。

上述库均遵守“一模型一数字化库”。当前0622文件没有给“标识关联配置库”具体关联行，因此只建设库结构，不得伪造关联案例；后续由标识关联配置模型正式产生数据。

## 5. 业务分类与模型数字化配置

模型运行时以模型数字化编码匹配“模型数字化配置数字化库”，取得该模型的业务分类数字化属性集合与数字化标识集合。审批、智选均以这些正式配置为入口，禁止按中文模型名称猜测业务领域。

0622已给出的采购合同签订、采购计划编制、出差审批、安全隐患整改、会议收集、会议组织、会议展示、会议纪要，以及审批模型 `5011001099001001001`、智选模型 `5011001099001001002` 等记录应作为系统初始化案例数据保留。用户已于2026-09-21明确确认：`5011001006001001001` 当前唯一对应“会议收集模型”。源文件中同码“环保整改审批模型”条目仅作为源文档历史差异留痕，不得作为当前模型数字化配置、不得注册为可运行模型，也不得再次形成同码冲突。

## 6. 配置数据的字段与编码边界

配置数字化库中的中文业务列可以作为结构化配置字段保存；只有源文档已经正式分配数字化标识的字段，才能写入对应数字化标识列。不得为了让表格“看起来完整”而自行编造新的19位数字化标识。

## 7. 规则数据化

审批阈值、审批分管、人员组织、模型时限、智选标识关联等全部从相应数字化库读取。复杂算法由引擎执行，但输入必须来自正式数字化属性、数字化标识和模型·库记录。

## 8. 配置版本与历史数据

已发布数字化配置保留版本。新结构上线后，历史16位数据不物理删除；迁移只放宽兼容校验并新增当前结构数据。旧数据仍可追溯，但新数据按本文件第2章执行。

# 04 数字化规则与配置

## 1. 数字化目标

数字化不是把纸质表单变成网页，而是把业务对象、规则、状态和模型关联转化为可计算、可存储、可关联、可触发的统一数字化数据。

## 2. 数字化三要素

### 2.1 编码（Code）

用于确定数字化对象、模型或业务对象的唯一性。模型的唯一身份就是其数字化编码，系统不再另设模型 ID。

### 2.2 属性（Attribute）

用于描述类别、层级、业务特征、运算维度和筛选特征。

### 2.3 标识（Label/Identifier）

用于表达一次模型运行形成的有效业务结果、状态或关联触发条件。

数字化编码、属性、标识应由统一数字化配置维护，不允许不同模块自建互不兼容编码体系。必须区分：数字化编码负责唯一性，模型文件名负责一次运行记录，数字化标识负责结果/状态/触发。

## 3. 唯一性与运行记录口径

- 模型唯一性：只认数字化编码。
- 模型运行记录：每次运行只认本次生成的模型文件名。
- 来源链路：通过来源模型文件名关联上一步运行记录。
- 运行结果与触发语义：使用数字化标识表达。
- 禁止引入模型 ID、实例 ID 作为与上述机制并列或替代的业务标识。

## 4. 16 位结构

项目采用统一 16 位数字化结构时：

- 具体位段、长度和含义必须来自统一配置；
- 业务开发不得自行扩展位数或改变位段含义；
- 变更结构必须有版本及迁移策略；
- UI 显示名称不能代替数字化编码。

## 5. 数字化配置至少包含

- 模型与库的唯一关系
- 字段与数字化属性映射
- 数字化标识生成规则
- 标识与模型的关联关系
- 数据存储规则
- 数据校验规则
- 外部数字化库数据来源
- 发布范围与版本
- 触发规则

## 6. 规则数据化

可由配置表达的规则，不应散落为代码中的常量或 if/else：

- 审批阈值
- 审批层级
- 人员与岗位
- 会议类型
- 智选关联
- 定时周期
- 定量阈值
- 预设意见/业务意见项
- 字段选项

复杂计算可由引擎执行，但其输入参数和业务映射仍应配置化。

## 7. 数字化标识存储

进入正式数字化库的标识必须有清晰语义、来源和版本。临时 UI 变量、组件状态、前端缓存值不得冒充数字化标识。

## 8. 配置版本

数字化配置必须支持至少：

`草稿 → 校验 → 发布 → 版本冻结 → 新版本修改`

已发布配置不得被无痕覆盖。
