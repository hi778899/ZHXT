# V17.7.26 当前增补——审批/智选基础模型库数据来源

审批与智选所依赖的基础数字化库只接受对应数据产生模型的正式运行结果。`system_initialization`、`system_sync` 是模型启动方式，不是直接写库方式。正式基础记录必须具有真实 `run_id`；历史0622数据仅作为历史来源，经模型运行物化后方作为当前数字化库数据使用。

# V17.7.22 当前增补——模型时限数字化库当前有效值

模型时限数字化库是规定时限唯一正式数据源。人工模型时限记录必须完成审批同意后才可成为当前有效配置；数字化标识值优先于历史中文字段。系统初始化8值只作为基线，不得覆盖后续已审批生效配置。

# V17.7.16 当前增补——相对级次数字化数据来源

行政审批、技术审查、业务审查均以发起人为起点计算相对流程级次。组织数字化库中的组织数字化属性是相对审批/审查级次计算及实际节点匹配的正式数据依据之一；组织名称数字化属性、岗位/职务属性用于共同定位组织与人员。上述字段属于内部运算数据，普通审批界面只展示最终审批路径。所有来源模型统一执行，详见 `20_APPROVAL_RELATIVE_LEVEL_RULES.md`。

# V17.7.9 当前增补——员工数字化配置同步与请休假审批

1. 请休假审批定位申请人时，正式数据源仍为员工信息数字化库，不得直接以 `users` 表字段代替审批人员配置。
2. 系统账号是员工数字化配置的初始化/同步来源。已启用账号在缺少正式0622员工记录时，应先确保当前11位员工数字化编码，再按所属部门匹配组织名称数字化库，将组织数字化属性、组织名称数字化属性、业务领域、身份和 `数据版本=0622` 写入员工信息数字化库。
3. 已存在 `src0622-*` 等正式员工数字化记录时，自动同步不得覆盖该正式配置。
4. 系统管理员权限与组织岗位分离：`admin` 仅表示系统权限，不能作为审批职级；缺少正式岗位配置时按所属组织普通员工初始化，后续应通过员工信息模型正式维护。
5. 部门经理/部门负责人在员工信息数字化库中形成“正职/负责人”组织数字化属性，并取得考勤管理业务领域；考勤主管形成“业务审核岗”。普通员工形成所属组织“办事员”属性。
6. 请休假及其他所有模型的审批/审查级次统一采用相对流程级次；组织层级与岗位属性只作为人员匹配数据，不作为审批级次。
7. 若用户所属部门无法在组织名称数字化库匹配，必须明确提示“申请人所属部门未匹配到组织名称数字化配置”，不得伪造组织。

# 06 数字化库与数据源规则

## 1. 唯一库概念

系统只使用“数字化库”这一库概念，不另设其他库分类。

所有数字化库均由模型唯一对应并通过模型运行形成、维护数据：

`模型 → 运行 → 本模型数字化库`

当其他模型需要引用这些数据时，通过数据源配置读取对应数字化库：

`模型 A ← 数据源配置 ← 模型 B 数字化库`
## 1.1 模型业务数据唯一正式来源

模型业务数据的唯一正式来源是其归属数字化库。`model_runs`、`run_id`、模型文件名、待办记录等只负责运行身份、状态、关联和追溯，不得替代数字化库成为业务字段的最终展示来源。

统一读取链路：

`run_id / 模型文件名 → 定位模型运行 → 定位对应数字化库 → 按数字化标识读取正式数据 → 页面展示/后续模型使用`

因此：

- 业务模型字段读取业务模型数字化库；
- 审批结果、审批办理结果读取审批模型数字化库；
- 智选判断与关联启动结果读取智选模型数字化库；
- 规定时限读取模型时限数字化库；
- 人员、组织、业务分类、审批分管等分别读取其对应数字化库；
- `todo.content`、`model_runs.input_data/output_data` 可作为运行过程留痕或历史兼容定位信息，但不得作为当前正式业务数据源。


例如，人员选择读取“人员信息模型”的数字化库；部门选择读取“组织/部门模型”的数字化库；会议类型、审批层级、审批时限、数字化配置等也分别读取其对应模型的数字化库。

### 1.2 审批/审查相对级次的数据来源

审批模型的目标不再以绝对组织层级表达。正式配置应分别形成：基础行政审批级次、最终行政审批级次、技术审查级次、业务审查级次。

基础行政审批级次读取链路：

`来源模型数字化编码 → 模型数字化配置数字化库 → 业务分类数字化属性 → 审批分管配置数字化库 → 基础行政审批级次`

阈值/特殊属性配置只调整相对级次，例如“增加一级审批”，不得实现为“由四级机构调整到三级机构”。

组织数字化库、组织名称数字化库、组织关系数字化库、员工信息数字化库负责根据每个相对级次定位实际组织、岗位和人员。组织绝对层级是匹配条件，不是审批级次。

技术审查、业务审查分别读取其分管配置并形成独立相对级次。未匹配到正式相对级次配置时，应明确提示对应配置缺失，不得从历史绝对层级目标反推。

## 2. 需要绑定数字化库的数据场景

凡字段的数据不是由当前用户自由输入，而是需要从系统既有数据中选择、查询或联动取得，都应通过数据源绑定相应数字化库，例如：

- 下拉框
- 单选
- 多选
- 人员
- 部门
- 岗位
- 组织
- 会议类型
- 审批层级
- 业务意见项
- 业务类别
- 状态分类
- 数字化配置项
- 其他模型运行结果

## 3. 一处形成，多处读取

一项业务数据只能由其归属模型负责形成并写入本模型数字化库。其他模型如需使用，应读取该数字化库，不应复制形成另一份静态数据。

多个模型、多个字段允许同时读取同一数字化库。例如请休假、审批、会议等多个模型均可读取员工信息数字化库中的人员数据。

## 4. 数据源配置

字段数据源至少应描述：

- 来源模型
- 来源数字化库
- 查询条件
- 显示字段
- 值字段（需要跨模型稳定关联时优先使用相应数字化编码）
- 排序规则
- 有效数据筛选条件
- 依赖字段
- 权限过滤
- 数据版本或生效条件（如业务需要）

数据源本身应由模型配置保存，不得只存在于前端临时状态。

## 5. 禁止硬编码和复制数据

禁止：

- 在 React/Vue 等组件中写固定人员、部门、会议类型等业务列表；
- 在后端代码中维护业务枚举来替代应由模型数字化库提供的数据；
- 每增加一个数据项就修改并发布代码；
- 将其他模型数字化库的数据复制一份作为当前模型长期维护的数据源；
- 使用显示名称、模型 ID 或实例 ID 作为跨模型稳定关联依据；模型身份使用数字化编码，运行记录使用模型文件名。

## 6. 数字化配置本身也遵循一模型一数字化库

数字化配置、审批配置、智选配置、人员信息、组织信息、会议类型、审批层级、审批时限等基础数据，同样必须由相应模型建设、运行并形成对应数字化库，不得因为属于“系统配置”就绕开“一模型一数字化库”。

## 7. 写入边界

读取其他模型数字化库不代表拥有写入权限。模型只能将本次运行形成的正式结果写入本模型数字化库。

若需要改变另一个数字化库中的业务数据，应启动其对应模型，通过该模型运行完成变更并形成新的有效结果，禁止跨模型直接写库。

## V17.7.11 数字化库运行文件名一致性

数字化库是模型业务数据唯一正式来源，同时每条运行记录必须使用当前统一模型文件名定位。既有数字化库中的旧格式模型文件名必须迁移为 `模型数字化编码-员工数字化编码-时间码`，并与对应运行记录、来源运行和下游关联同步。页面、审批、智选不得通过旧文件名读取一套数据、通过新文件名读取另一套数据。

## V17.7.13 数字化库文件名展示与数据源一致性

数字化库记录列表中的“文件名”只允许显示该记录持久化保存的标准模型文件名。禁止使用 `record_id`、数据库 UUID、seed 编号或其他内部键作为显示兜底。

所有数字化库，无论是业务运行库还是员工、组织、时限、审批分管等配置类数字化库，均执行同一模型文件名格式。历史系统初始化记录通过迁移形成标准文件名；以后配置数据的正式变更应由对应模型运行形成文件记录。

## V17.7.14 数字化库数据形成来源

数字化库既是模型业务数据的唯一正式数据源，也必须保存该数据的模型运行来源。任何正式记录必须能从 `run_id` 追溯到对应数据产生模型的一次真实 `model_runs`。

系统基础数据和配置数据同样遵守本规则：员工、组织、业务定义、数字化定义、数字化标识、模型时限、审批分管、审批意见、标识关联等数据的初始化或同步，必须运行其对应数据产生模型后入库。不得以“系统初始化”“标准数据”“seed 数据”为理由直接插入 `run_id=NULL` 的正式记录。

查询页面中的“文件名”显示 `digital_library_records.file_name`；该值必须来自同一次模型运行，禁止显示 `record_id`、`std-*`、`src0622-*`、UUID 等技术键作为替代。
