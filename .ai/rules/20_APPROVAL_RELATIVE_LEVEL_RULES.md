# V17.7.18 当前增补——相对级次只负责生成路径，Path_final 才负责执行与完成判定

- 行政审批级次、技术审查级次、业务审查级次用于生成各自子路径，不能单独作为审批模型完成条件。
- `Path_final = Merge(Path_approval, Path_technical_review, Path_business_review, 路径配置) → 去重后的正式办理路径`。
- 正常同意流程必须逐一完成 `Path_final` 中全部必经节点；只要仍有未完成必经节点，审批模型不得归档。
- 员工请休假示例：`员工发起 → 部门经理审批 → 考勤主管业务审查 → 办结`。部门经理完成表示行政审批子路径完成，但整条审批尚未完成；必须继续到考勤主管。
- 只有考勤主管等 `Path_final` 最后必经节点完成后，审批模型才能正常归档并触发智选。
- 若节点结果命中正式终止规则，则可以提前结束剩余路径，但必须以“终止结果”归档，并继续触发智选。

# 20 全系统相对审批/审查级次与最终路径展示规则

> 当前有效版本：V17.7.19  
> 本规则适用于系统内所有进入通用审批模型的来源模型，包括普通业务模型、四阶段建设模型、会议类模型及以后新增模型。

## 1. 核心原则

审批级次、技术审查级次、业务审查级次均为**以本次业务发起人为起点的相对流程级次**。组织绝对层级不直接等同于审批级次。

- 发起人不计审批/审查级次；
- 从发起人出发匹配到的第一个有效行政审批节点为“一级审批”；
- 第二个有效行政审批节点为“二级审批”，依次类推；
- 技术审查路径独立编号：一级技术审查、二级技术审查……；
- 业务审查路径独立编号：一级业务审查、二级业务审查……；
- “三级机构、四级机构、五级机构”等组织层级只属于组织数字化属性的一部分，不作为普通用户界面的审批级次展示值。

## 2. 组织数字化属性与审批级次

组织数字化库中的**组织数字化属性**是审批级次计算的正式数据依据之一，用于确定组织、内设职级、岗位/职务及其在本次路径中的相对位置。

统一计算原则：

`发起人员工数字化编码 → 员工信息数字化库 → 发起人组织名称数字化属性/组织数字化属性 → 组织数字化库 → 组织关系数字化库 → 候选组织数字化属性 → 审批分管配置数字化库 → 实际人员 → 相对审批/审查级次`

要求：

1. 组织数字化属性与审批级次的关系必须来自组织数字化库及正式审批/审查配置，不得在前端或审批代码中写死；
2. 发起人所在组织及其组织数字化属性作为本次路径起算依据；
3. 沿组织关系寻找下一候选组织/岗位时，读取该组织的组织数字化属性；
4. 只有该组织数字化属性最终匹配到真实有效审批/审查人员时，才形成一个相对级次；
5. 行政审批、技术审查、业务审查分别独立形成自己的相对级次；
6. 组织数字化属性、相对级次及匹配过程属于内部运算数据，不直接展示给普通审批用户。

例如：

`员工发起 → 部门经理 → 考勤主管`

内部可形成：

- 部门经理对应的组织数字化属性 → 一级行政审批；
- 考勤主管对应的组织数字化属性/岗位属性 → 一级业务审查。

但普通审批界面不显示“一级审批”“一级业务审查”及对应组织数字化属性，只显示最终路径节点。

## 3. 内部审批/审查级次计算

系统内部仍分别维护：

- `A_base`：基础行政审批级次；
- `A_final`：最终行政审批级次；
- `T_final`：技术审查级次；
- `B_final`：业务审查级次。

这些字段只用于模型运算、路径生成、审计追溯和回归测试，不作为普通审批界面的展示字段。

内部行政审批计算链：

`来源模型数字化编码 → 模型数字化配置数字化库 → 业务分类数字化属性 → 审批分管配置数字化库 → A_base → 数字化标识阈值/特殊属性调整 → A_final`

技术审查、业务审查按各自配置独立计算目标级次。

阈值调整必须作用于相对级次，例如“增加一级审批”；不得把“增加一级”实现为“四级机构改为三级机构”。

## 4. 组织逐级路径仅作为内部运算

组织逐级路径继续作为审批引擎内部算法，但不在普通审批界面展示。

内部计算流程：

1. 从发起人员工数字化编码读取发起人组织；
2. 读取当前组织的组织数字化属性、组织名称数字化属性；
3. 按审批分管配置匹配当前业务的候选岗位/人员；
4. 若形成真实有效人员节点，则计入当前相对审批/审查级次；
5. 若未达到内部计算所需目标级次，则通过组织关系数字化库进入下一组织；
6. 进入新组织后重新读取其组织数字化属性、审批分管配置和员工信息；
7. 继续寻找下一有效节点；
8. 达到内部目标级次后结束对应路径计算。

单纯跨组织不增加级次；只有形成真实有效人员节点时才增加级次。

## 5. 行政审批、技术审查、业务审查独立计算后合并

系统内部先分别得到：

- `Path_approval`：行政审批路径；
- `Path_technical_review`：技术审查路径；
- `Path_business_review`：业务审查路径。

再按模型配置的串联、插入或并联规则合并为：

`Path_final`

`Path_final` 是普通审批界面唯一需要展示的审批路径。

## 6. 人员去重

同一实际人员在行政审批、技术审查、业务审查或多个组织匹配中重复出现时，按现行规则去重并保留靠后的有效环节。

去重按实际员工数字化编码判断，不按岗位名称、节点名称判断。

去重后的 `Path_final` 才能进入普通审批界面。

## 7. 普通审批界面展示规则

普通用户审批界面**不得显示**下列内部运算字段或中间过程：

- 基础审批目标；
- 最终审批目标；
- 基础行政审批级次；
- 最终行政审批级次；
- 技术审查目标层级；
- 业务审查目标层级；
- 技术审查级次；
- 业务审查级次；
- 组织逐级路径；
- 组织数字化属性匹配过程；
- 命中数字化标识阈值；
- 阈值调整过程；
- 审批路径计算依据；
- 审批人计算依据。

以上数据仍必须在模型内部保存，用于运算、审计和问题追溯，但不得作为普通审批办理页面的可见字段。

普通审批界面只显示**运算后的最终审批路径 `Path_final`**。

### 7.1 最终审批路径节点显示格式

每个节点统一显示为：

`岗位/角色名称（员工数字化编码）`

多个节点按实际办理顺序用 `-` 或箭头连接。

例如员工请休假：

`部门经理（部门经理员工数字化编码）-考勤主管（考勤主管员工数字化编码）`

实际编码示例：

`部门经理（50110020015）-考勤主管（50110020023）`

界面不得再附加：

- “一级审批”；
- “一级业务审查”；
- “五级机构·正职/负责人”；
- “基础目标”；
- “最终目标”；
- “命中阈值”等说明。

如岗位/角色名称无法取得，可使用正式人员名称，但必须同时显示员工数字化编码；不得只显示姓名而没有数字化编码。

## 8. 审批办理记录与最终路径分离

最终审批路径用于说明本次审批实际应经过哪些节点。

审批办理记录用于记录每个已办理节点的实际办理事实，包括：

- 审批/审查人；
- 到达时间；
- 办理时间；
- 耗时；
- 审批意见；
- 审批结果。

审批办理记录仍不得展示“本环节审批/审查要求”和“规定时限”；耗时继续按“办理时间－到达时间”计算。

## 9. 内部审计数据必须保留

虽然普通审批界面不展示中间运算，但审批模型内部及审批模型数字化库仍必须保存可追溯数据，包括：

- 发起人组织数字化属性；
- 各候选组织数字化属性；
- 各节点对应的相对审批/审查级次；
- 基础/最终行政审批级次；
- 技术/业务审查级次；
- 组织逐级路径；
- 命中的数字化标识与阈值；
- 阈值调整结果；
- 审批分管配置；
- 人员匹配依据；
- 去重前路径；
- 去重后最终路径。

普通页面隐藏不等于删除内部数据。

## 10. 全系统适用范围

凡进入通用审批模型的来源模型均执行本规则，不允许某个模型单独恢复“展示基础目标/最终目标/组织逐级路径/阈值命中”的旧界面。

包括但不限于：请休假、采购、合同、会议事项、设备、物资、科技创新、四阶段建设模型以及以后新增模型。
## 10. V17.7.17 代码落地要求

- 所有当前审批运行必须在路径去重后重新按行政审批、技术/业务审查分别连续编号；不得沿用组织绝对层级名称作为审批级次。
- `Path_final` 必须来自已经解析到实际员工数字化编码的有效节点。
- 普通审批待办、已办、办结不得渲染 `审批路径计算`、`审批人计算`、`基础审批目标`、`最终审批目标`、`组织逐级路径`、`命中数字化标识阈值` 等中间区块。
- 普通审批界面的路径展示节点不带组织层级、不带阈值解释、不带“审批人：姓名”说明，统一为“岗位/角色名称（员工数字化编码）”。
