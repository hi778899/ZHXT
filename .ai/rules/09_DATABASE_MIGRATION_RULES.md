# 09 数据库与 Migration 规则

## 1. 数据分类

至少区分：

- 模型元数据
- 模型版本
- 模型字段/布局/规则
- 数字化配置
- 数字化库运行记录数据（以模型文件名识别每次运行记录）
- 其他模型数字化库数据
- 审批运行数据
- 智选运行数据
- 用户/组织/权限
- 运行日志
- 审计日志

## 2. 数据库变更

所有数据库结构变化必须通过 migration 管理，禁止：

- 手工修改生产数据库后不留脚本；
- 应用启动时无条件 drop/create；
- 为解决开发问题清空正式数据；
- 无版本地重命名/删除字段。

## 3. Migration 要求

每个 migration 应明确：

- 变更目的
- 升级操作
- 对现有数据的影响
- 数据回填策略
- 索引/约束变化
- 回滚或恢复策略

## 4. 数字化库创建

四阶段发布新模型时，数字化库可以采用物理表、逻辑表或统一运行表等实现，但必须满足“一模型一库”的逻辑隔离、可追溯和唯一归属。模型归属通过数字化编码确定，每次模型运行记录通过模型文件名识别；不得因为底层复用物理表而引入模型 ID/实例 ID 作为另一套业务身份机制。

## 5. 生产数据安全

部署前必须备份关键数据。高风险 migration 应先在与生产结构一致的测试环境验证。

## 6. V17.7.11 模型文件名全量迁移

当系统模型文件名规则升级时，migration 必须覆盖运行记录和数字化库既有数据，而不是只影响新数据。迁移至少包括：

1. 建立旧文件名到新文件名的一一映射；
2. 使用当前19位模型数字化编码、11位员工数字化编码和原运行时间生成新文件名；
3. 更新本次模型文件名；
4. 更新来源模型文件名及业务→审批→智选→后续模型的全部关联引用；
5. 更新对应数字化库、待办、已办、办结、驾驶舱关联数据和需要依赖文件名追溯的日志/审计数据；
6. 保留原文件名迁移审计信息；
7. 迁移前后执行数量、唯一性、外部引用、孤儿引用和模型簇完整性校验。

文件名迁移必须具备事务/分阶段可恢复机制。禁止出现 `model_runs` 已更新而数字化库或下游来源文件名仍为旧值的半迁移状态。
