# 09 数据库与 Migration 规则

## 1. 数据分类

至少区分：

- 模型元数据
- 模型版本
- 模型字段/布局/规则
- 数字化配置
- 数字化库运行记录数据（以模型文件名识别每次运行记录）
- 其他模型数字化库数据
- 审批运行数据
- 智选运行数据
- 用户/组织/权限
- 运行日志
- 审计日志

## 2. 数据库变更

所有数据库结构变化必须通过 migration 管理，禁止：

- 手工修改生产数据库后不留脚本；
- 应用启动时无条件 drop/create；
- 为解决开发问题清空正式数据；
- 无版本地重命名/删除字段。

## 3. Migration 要求

每个 migration 应明确：

- 变更目的
- 升级操作
- 对现有数据的影响
- 数据回填策略
- 索引/约束变化
- 回滚或恢复策略

## 4. 数字化库创建

四阶段发布新模型时，数字化库可以采用物理表、逻辑表或统一运行表等实现，但必须满足“一模型一库”的逻辑隔离、可追溯和唯一归属。模型归属通过数字化编码确定，每次模型运行记录通过模型文件名识别；不得因为底层复用物理表而引入模型 ID/实例 ID 作为另一套业务身份机制。

## 5. 生产数据安全

部署前必须备份关键数据。高风险 migration 应先在与生产结构一致的测试环境验证。

## 6. V17.7.12 模型文件名全量迁移

当系统模型文件名规则升级时，migration 必须覆盖运行记录和数字化库既有数据，而不是只影响新数据。迁移至少包括：

1. 建立旧文件名到新文件名的一一映射；
2. 使用当前19位模型数字化编码、11位员工数字化编码和原运行时间生成新文件名；
3. 更新本次模型文件名；
4. 更新来源模型文件名及业务→审批→智选→后续模型的全部关联引用；
5. 更新对应数字化库、待办、已办、办结、驾驶舱关联数据和需要依赖文件名追溯的日志/审计数据；
6. 保留原文件名迁移审计信息；
7. 迁移前后执行数量、唯一性、外部引用、孤儿引用和模型簇完整性校验。

文件名迁移必须具备事务/分阶段可恢复机制。禁止出现 `model_runs` 已更新而数字化库或下游来源文件名仍为旧值的半迁移状态。


## V17.7.12 文件名迁移约束顺序

1. 对系统内置且仍使用历史16位模型编码的模型，必须先建立正式19位模型编码映射，再迁移模型运行文件名。
2. 文件名 CHECK 约束必须在历史记录迁移、异常标记之后建立；`NOT VALID` 仍会约束建立之后的 INSERT/UPDATE，不得将其误认为不会校验后续更新。
3. 无法安全映射的历史记录必须先写入 `legacy_file_name` 与迁移异常清单；约束允许该原始历史行继续被查询和维护，但不得用于形成新的跨模型运行关系。
4. 新插入或新生成的模型运行不得利用 `legacy_file_name` 绕过当前文件名规则。

## 7. V17.7.14 历史数字化库记录模型运行物化

升级时必须扫描全部 `digital_library_records.run_id IS NULL` 的历史记录。对能够安全确定数据产生模型、当前19位模型数字化编码和当前11位运行人员员工数字化编码的记录，使用原 `created_at` 形成 `system_initialization` 运行，并一次性回填 `run_id`、标准 `file_name`、显示文件名和运行来源。

不能安全物化的记录进入 `digital_library_run_materialization_issues`；不得猜测绑定模型或人员。`migration_pending` 仅作为迁移暂存状态，待 seed 发布/补齐数据产生模型后必须自动重试物化。

数据库必须设置写入约束：正常新增/更新的正式数字化库记录若 `run_id` 为空，写入失败；具有 `run_id` 时其标准文件名必须符合当前格式。迁移完成后 `std-*` 等历史主键只允许保存在 `legacy_record_id` 审计字段。
