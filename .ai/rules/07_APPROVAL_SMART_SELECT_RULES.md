# 07 通用审批与智选规则

> 当前有效版本：V17.7.17 规则修订
> 本次修订重点：全系统审批、技术审查、业务审查统一改为以发起人为起点的相对流程级次；组织绝对层级仅用于组织/人员匹配。

## 1. 通用审批与智选链路

继续执行：

`业务模型数字化库 → 审批模型 → 审批模型数字化库 → 智选模型`

审批模型正式归档并写入审批模型数字化库后，由数字化库硬性触发智选模型。不得由前端按钮直接创建智选，也不得由驾驶舱自行推断智选状态。

该触发是**系统固定硬性链接**，不是普通可选模型关系。运行引擎必须保证：

1. 审批模型最终归档成功；
2. 审批模型数字化库正式记录写入成功；
3. 立即启动唯一通用智选模型；
4. 智选模型建立独立 `model_runs` 运行记录并生成自己的模型文件名；
5. 智选完成本次判断并写入智选模型数字化库；
6. 向原业务发起人产生本次智选结果待办/待确认事项。

上述第3步不得以审批模型 `relations`、`afterArchiveEnabled`、`nextModelName` 或历史版本配置是否完整作为前提。历史配置缺失、被删除或被禁用时，系统仍必须执行审批→智选。

审批结果是否同意不决定“是否启动智选”。审批不同意或其他终止结果仍要进入智选，由智选模型读取审批结果后终止正常关联或执行相应特殊判断。

## 2. 智选模型启动事实

智选模型一旦满足下列任一条件，即视为已经启动：

- 已生成智选模型运行记录；
- 已生成智选模型文件名；
- 已产生智选模型待办；
- 已有智选已办/办结；
- 已有智选模型数字化库正式记录。

驾驶舱和已办/办结查询时必须实时解析上述事实。禁止继续使用审批归档瞬间保存的旧关联状态，导致“智选待办已存在、关联模型仍显示未启动”。

智选结果待办归属原业务发起人。最后一个审批人与原业务发起人不是同一人时，不要求最后审批人在自己的待办中看到该智选结果，但原业务发起人的“我的待办”必须能够看到。

无后续关联模型不等于“不启动智选”。此时智选结果应明确记录“无后续关联模型”，仍然形成智选运行事实和待办。

### 2.1 智选模型查看主键与数据来源

智选模型完成运行后，`model_runs.id` 仅作为本次智选运行的定位主键。我的已办、我的办结、业务模型关联模型三个入口必须传递并复用同一 `smart_run_id`。

正式读取链路固定为：

`smart_run_id → 定位智选运行/来源审批运行/原业务运行 → 定位各自对应数字化库 → 按数字化标识读取正式数据`

数据归属必须严格区分：

- 模型文件名、运行状态、运行时间、关联 run_id：由 `model_runs` 提供定位与追溯；
- 原业务内容：读取原业务模型数字化库；
- 审批结果及审批正式结果：读取审批模型数字化库；
- 统计/智选判断、关联模型集合和启动明细：读取智选模型数字化库；
- `todo.content`、已办/办结列表快照、`model_runs.input_data/output_data` 不作为详情业务字段的正式来源。

智选详情固定展示：模型信息、业务内容、审批结果、统计分析、智选判断、关联模型启动明细。无后续关联模型、审批未通过或启动次数为0时，只展示实际字段值（如“无”“0”“未形成”），不增加“完整、有效”等解释性结论。任何单字段缺失不得导致整个页面不渲染。

## 3. 智选运行逻辑

智选模型仍严格执行最新有效规则：

1. 接收审批模型文件名；
2. 沿审批模型输入链追溯原业务模型，取得业务模型名称、业务模型文件名、中文显示名称、业务数字化标识和业务运行记录；
3. 将追溯结果回填为智选模型正式输入字段后，再执行智选模型设计校验与运算；不得出现“内部已追溯到业务、但中文必填字段仍为空”导致智选启动失败；
4. 读取审批模型正式数字化库记录；
5. 先启动统计分析模型；
6. 判断审批结果；
7. 先特殊、后正常；
8. 计算待处理数字化标识集合；
9. 读取标识关联配置数字化库；
10. 筛选有关联数字化标识集合；
11. 对每个有关联标识按有效数据条数展开模型启动实例；
12. 每个实例生成真实模型文件名；
13. 汇总并写入智选模型数字化库。

多标识、多数据、多次触发规则继续有效，不得按目标模型去重为一次运行。

## 3.1 全系统相对审批/审查级次计算

所有进入通用审批模型的来源模型统一执行相对级次规则，不区分请休假、采购、会议或其他业务类型。

行政审批统一链路：

`来源模型数字化编码 M → 模型数字化配置数字化库 → 业务分类数字化属性 → 审批分管配置数字化库 → 基础行政审批级次 A_base → 阈值/特殊属性调整 → 最终行政审批级次 A_final → 实际行政审批路径`

其中：

- 发起人不计级次；
- 从发起人出发的第一个有效行政审批节点为一级审批；
- 第二个有效行政审批节点为二级审批，依次类推；
- 跨越组织但未形成有效审批人时不增加级次；
- 组织层级、岗位/职务属性只用于找到具体人员，不等于审批级次；
- 阈值调整作用于相对级次，如“+1级”，不得直接把四级机构改为三级机构。

技术审查与业务审查分别独立计算：

- 第一个有效技术审查节点 = 一级技术审查；
- 第一个有效业务审查节点 = 一级业务审查；
- 两者不占用行政审批的级次序号，也互不占用。

例如员工请休假：

`员工发起 → 一级审批：部门经理 → 一级业务审查：考勤主管 → 办结`

普通用户审批界面不得显示基础行政审批级次、最终行政审批级次、技术/业务审查级次、组织逐级路径、组织数字化属性匹配过程和命中数字化标识阈值等中间运算信息。上述内容仅作为内部运算和审计数据保存。普通审批界面只显示运算后的最终审批路径 `Path_final`，节点格式统一为“岗位/角色名称（员工数字化编码）”。

完整路径、组织跳转、自审批跳过和去重规则见 `20_APPROVAL_RELATIVE_LEVEL_RULES.md`。

## 4. 审批内部计算与用户界面分离

审批模型内部必须继续计算并保存：审批路径计算依据、正式审批路径节点、审批人计算依据、本环节审批/审查要求等数据。这些数据属于模型运算和审计留痕，不得删除。

但普通用户界面不直接展示下列技术字段：
- 基础审批目标；
- 最终审批目标；
- 基础行政审批级次；
- 最终行政审批级次；
- 技术审查目标层级/级次；
- 业务审查目标层级/级次；
- 组织逐级路径；
- 组织数字化属性匹配过程；
- 命中数字化标识阈值及阈值调整过程；

- 审批路径计算 → `审批路径计算依据`；
- 审批路径计算 → `正式审批路径节点`；
- 审批人计算 → `审批人计算依据`；
- 审批人计算 → `本环节审批/审查要求`；
- 审批办理记录 → `本环节审批/审查要求`；
- 审批办理记录 → `规定时限`；
- 审批办理记录 → `审批人计算依据`；
- 审批办理记录 → `审批路径计算依据`。

普通审批界面唯一展示的路径结果为 `Path_final`，节点格式为“岗位/角色名称（员工数字化编码）”，例如“部门经理（50110020015）-考勤主管（50110020023）”。

这些字段可以保存在审批模型运行结果、数字化库、后台审计数据中，但不得作为普通审批办理、已办、办结页面的直接展示项。

## 5. 规定时限与审批办理记录耗时

“规定时限”是审批节点内部运算数据，不是说明文字；它继续用于节点提醒、应完成时间和超时判断。

统一计算：

`来源业务分类数字化属性/业务领域 → 模型时限数字化库 → 当前有效模型时限数值`

用户界面必须显示查得的实际数值，例如源数据命中 `8`，页面显示 `8`；命中 `16`，页面显示 `16`。

禁止显示：

- `按数字化库配置`；
- `来自数字化库`；
- `按配置计算`；
- 其他代替实际时限数值的说明文字。

若没有匹配到有效时限，显示 `未配置`；不得伪造数值。

若同一业务同时命中多条有效时限配置，必须先由数字化库配置规则收敛为唯一当前有效值，页面不得自行取最大值、最小值或拼接多个值。

0622当前源数据未定义时限单位，因此在没有正式单位配置前，只展示正式数值，不由AI自行追加“小时”“天”“工作日”等单位。

### 5.1 当前审批办理页的规定时限取值

“本环节办理信息”属于当前节点办理信息，不属于历史“审批办理记录”，因此继续显示当前节点规定时限。

规定时限的唯一正式来源是**模型时限数字化库**。运行时应依据来源业务分类数字化属性/业务领域及当前节点适用条件查询模型时限数字化库，收敛出唯一有效值后用于当前节点。

统一关系：

`当前审批节点 → 业务分类数字化属性/业务领域 → 模型时限数字化库 → 当前有效规定时限`

`审批人计算.规定时限`、`currentTimeoutValue`、审批模型 output 中保存的规定时限均属于本次运算留痕/传递值，不得反向作为规定时限的数据源。若模型时限数字化库无匹配数据或同优先级冲突无法收敛，则显示 `未配置`；前端不得从快照、待办内容或其他页面补值。

### 5.2 审批办理记录

审批办理记录不展示上述规定时限。审批办理记录统一展示“耗时”：

`耗时 = 办理时间 - 到达时间`

耗时只能根据当前环节真实到达时间和真实办理时间计算；不得读取规定时限字段替代。未办结或时间无效时显示 `—`。

## 6. 验收

1. 智选待办存在后，已办关联状态不再显示未启动；
2. 审批用户界面不显示本规则第4章列出的技术字段；
3. 技术字段仍在后台运行结果中保留；
4. 当前审批节点“本环节办理信息”的规定时限必须由模型时限数字化库匹配取得；
5. `审批人计算`、待办快照和模型 output 中的规定时限仅作运算留痕，不得作为页面反向补值来源；
6. 审批办理记录不显示本环节审批/审查要求和规定时限；
7. 审批办理记录显示真实耗时，且等于办理时间减去到达时间；
8. 无时限配置时内部按未配置处理，不影响实际耗时计算；
9. 审批模型历史关系配置中缺少或禁用了智选关系时，审批归档仍必须启动智选；
10. 智选启动后必须生成真实智选运行实例和模型文件名；
11. 原业务发起人的“我的待办”必须出现智选结果事项；
12. 没有后续关联模型时仍必须生成本次智选运行和结果待办；
13. 审批、智选仍严格按照最新数字化库和模型运行逻辑执行；
14. 我的已办、我的办结和关联模型入口打开同一次智选时必须使用同一 `smart_run_id`；
15. 智选详情以 `model_runs` 定位运行，但业务字段必须分别读取原业务、审批、智选对应数字化库；
16. 智选无后续关联模型或历史字段缺失时仍必须正常显示详情，不得白屏。
17. 所有模型不得把三级/四级/五级机构等绝对组织层级直接作为审批/审查级次；
18. 行政审批、技术审查、业务审查必须分别以发起人为起点独立计算相对级次，并展示对应实际节点；
19. 未匹配到相对级次或对应节点配置时必须明确报对应配置缺失并停止错误路径生成，不得从历史绝对组织层级目标反推。

# 07 通用审批与智选规则

> 当前有效版本：V17.5。审批与智选均为全系统通用模型，并按0622数字化结构和《智选模型0729》运行结构执行。

## 1. 通用审批模型

审批模型唯一，正式模型数字化编码为 `5011001099001001001`。任意业务模型正式入库后，由业务模型数字化库硬性触发审批模型并传递业务模型文件名。审批模型按 `17_APPROVAL_MODEL_INTERNAL_LOGIC_RULES.md` 读取模型数字化配置、业务分类属性、审批分管、员工信息、组织关系和模型时限等数字化库，动态计算审批人、审批路径和办理时限。

审批模型业务内容必须动态承载来源业务模型，不得为请假、采购、合同等业务分别写专属审批结构。

## 2. 通用智选模型定位

智选模型唯一，正式模型数字化编码为 `5011001099001001002`。智选不是“后续模型按钮”，而是审批模型归档后由审批模型数字化库硬性触发的独立判断运算模型。

统一链路：

`审批模型运行 → 审批模型数字化库正式入库 → 硬性触发智选模型 → 接收审批模型文件名`

智选模型通过审批模型文件名追溯：

- 审批对象业务模型文件名；
- 审批结果；
- 来源业务模型数字化编码；
- 来源业务数字化属性；
- 来源业务数字化标识和值；
- 来源业务数字化库正式记录。

## 3. 智选固定运行顺序

智选模型启动后必须严格执行：

1. 接收并校验审批模型文件名；
2. 读取审批模型正式数字化库记录；
3. **先启动统计分析模型**；
4. 保存统计分析模型文件名/结果；如系统尚未配置统计分析模型，明确记录“统计分析模型未配置”，不得编造模型数字化编码；
5. 读取并判断审批结果；
6. **先特殊、后正常**；
7. 计算待处理数字化标识集合；
8. 读取标识关联配置数字化库；
9. 筛选有关联数字化标识集合；
10. 对每个有关联标识按其有效数据条数展开关联模型启动实例；
11. 每个实际启动实例独立运行并生成自己的模型文件名；
12. 汇总智选结果并写入智选模型数字化库。

## 4. 审批结果判断

- 审批不同意/终止：记录终止结果，不进入正常后续业务关联；
- 审批通过且命中特殊数字化条件：先进入特殊判断；
- 审批通过且无特殊条件，或特殊处理完成后允许继续：进入正常关联判断。

历史文档中的 `0.5` 仅保留在历史推演记录中，不作为当前通用中间状态。当前状态必须使用明确的审批结果和数字化标识表达。

## 5. 特殊判断

会议、纪要、统计等特殊分支也必须由数字化配置决定。不得把“会议纪要模型”或任何具体模型数字化编码硬编码在智选引擎。

`特殊数字化标识 → 标识关联配置数字化库 → 关联数字化标识 → 模型数字化配置数字化库 → 目标模型`

源文档给出的会议纪要模型编码只作为案例历史依据；实际触发必须查配置。

## 6. 正常标识关联

当前“标识关联配置数字化库”的字段口径为：

- 数字化标识；
- 关联数字化标识。

运行关系：

`来源业务数字化标识 → 标识关联配置数字化库 → 关联数字化标识 → 模型数字化配置数字化库.数字化标识集合 → 目标模型数字化编码`

0622源文档没有提供具体关联行，因此当前系统只建设并启用该库结构，不得自行填造关联数据。用户后续通过标识关联配置模型形成正式关系后，智选引擎自动读取。

## 7. 多标识、多数据、多次触发

这是智选强制规则。不能把“某标识存在”简化成目标模型只启动一次。

算法：

```text
待处理数字化标识集合 = 来源业务正式记录中的有效数字化标识

for 每一个待处理数字化标识 {
    查找标识关联配置数字化库
    若没有关联：继续下一个标识
    若存在关联：加入有关联数字化标识集合

    有效数据集合 = 本标识对应的有效数据
    for 有效数据集合中的每一条数据 {
        用关联数字化标识查模型数字化配置数字化库
        对每个匹配目标模型形成一个启动实例
        启动目标模型并生成该次模型文件名
    }
}
```

数组值按数组元素数计算数据条数；非空单值计1条；空值计0条。不同标识即使最终关联同一目标模型，也必须按各自有效数据实例展开，不得按目标模型名称去重后只运行一次。

## 8. 智选模型必须读取的数字化库

至少按需读取：

- 审批模型数字化库；
- 模型数字化配置数字化库；
- 标识关联配置数字化库；
- 来源业务模型数字化库；
- 统计分析模型数字化库（已配置时）；
- 会议等特殊业务数字化库（特殊判断命中时）。

## 9. 智选模型输出

用户可见和模型设计字段统一使用中文名称，至少包括：

- 智选模型文件名；
- 来源审批模型文件名；
- 审批对象业务模型文件名；
- 审批结果；
- 统计分析模型文件名；
- 统计分析结果；
- 待处理数字化标识集合；
- 有关联数字化标识集合；
- 各数字化标识有效数据条数；
- 特殊判断结果；
- 关联数字化标识；
- 关联模型；
- 关联数据；
- 关联模型启动次数；
- 被启动模型文件名；
- 触发结果；
- 智选结果；
- 智选完成时间。

英文技术键只允许内部兼容历史数据，不得作为新智选模型的字段名称。未由数字化配置正式分配的19位数字化标识不得由 AI 自行编造。

## 10. 验收

1. 智选必须由审批模型数字化库入库事件触发；
2. 智选能通过审批模型文件名追溯业务文件名和数字化标识；
3. 启动后先处理统计分析，再判断审批结果；
4. 审批终止不进入普通关联；
5. 特殊判断优先于普通关联；
6. 标识关联通过“标识→关联标识→模型数字化配置”解析目标模型；
7. 同一标识3条有效数据必须能够启动目标模型3次；
8. 每个目标运行必须生成真实模型文件名；
9. 标识关联配置库为空时不得虚构后续模型；
10. 智选结果完整写入智选模型数字化库。

# 07 通用审批与智选规则

> 当前有效版本：V17.4.1 补充规则
> 修订重点：审批模型必须承载全系统任意业务模型；业务内容动态加载；审批路径、审批层级、规定时限全部由数字化属性、数字化标识及相应模型·数字化库计算，不得按请假等单一业务写死。

## 1. 通用审批模型唯一口径

审批模型是全系统共用的通用模型，不对应“请休假审批模型”“采购审批模型”等一业务一套代码。任意通过四阶段建设并发布的业务模型，在业务数字化库正式入库后，都可以通过同一个通用审批模型进入审批。

业务模型只传递本次业务模型文件名、模型数字化编码、申请人员工数字化编码及正式入库记录引用。审批模型根据这些数据查询业务内容、数字化属性、数字化标识和审批配置。

## 2. 审批办理页面必须分成两类内容

### 2.1 业务内容区

业务内容区负责承载“本次被审批的业务模型内容”，必须动态适配任意业务模型。

读取链路：

`业务模型文件名 → 业务模型运行记录 → 模型数字化编码 → 模型设计/字段配置 → 本次业务数字化库记录 identifier_values → 动态展示`

规则：

- 不得写死申请人、请假类型、请假日期等请休假专属字段；
- 新建任何业务模型后，不应因为审批页面没有对应前端代码而无法审批；
- 业务内容字段名称、顺序、分组、附件/关联数据应以该业务模型的模型设计配置为准；
- 每个字段的正式值优先使用数字化标识对应值；
- 业务模型自身已有的数字化库记录是审批业务内容的正式数据来源。

### 2.2 本环节审批要求区

本环节“审批内容/审查内容”不是业务表单字段，而是审批模型根据当前节点类型、审批层级/岗位，从审批层级配置数字化库计算得到的本环节审查要求。

因此必须同时展示：

- 业务内容：被审批事项是什么；
- 审批要求：当前审批人需要审什么；
- 办理记录：路径如何生成、谁办过、时限如何确定、当前结果是什么。

### 2.3 审批模型字段命名必须使用中文

审批模型在模型设计、办理页面、已办、办结、数字化库展示中的新增字段名称必须使用中文业务名称。禁止新建 `sourceModelName`、`approvalRoute`、`approvalResult` 等英文业务字段。

历史运行数据中的英文技术键仅允许作为兼容读取键保留在运行引擎内部，不得作为当前审批模型的用户可见字段、模型设计字段或新写入字段口径。当前统一使用“前序业务模型、前序模型文件名、正式审批路径、审批结果、审批人计算、审批路径计算”等中文名称。

审批计算结果必须同时保留“审批人计算”和“审批路径计算”：每个正式路径节点都要明确实际审批/审查人、所在组织、审批层级/岗位、本环节要求、规定时限以及人员和路径的计算依据。正式审批路径不得只保存“行政审批→技术审查”等抽象环节名称。

## 3. 审批目标的计算

审批模型先从数字化库计算完整的基础审批目标，再计算阈值调整后的最终审批目标和具体审批人。

统一参数语义：

- `M`：业务模型数字化编码；
- `E`：申请人员工数字化编码；
- `I`：本次业务数字化标识集合；
- `A0`：申请人的组织数字化属性；
- `N0`：申请人的组织名称数字化属性；
- `T`：基础审批目标（完整审批对象，不是孤立层级）；
- `T'`：经过数字化标识阈值调整后的最终审批目标。

计算顺序：

1. `M` 匹配模型数字化库，读取数字化属性和数字化标识；
2. `M` 匹配审批层级分选数字化库，取得基础审批目标 `T`；
3. `I` 与审批阈值/层级调整配置逐条比较；
4. 命中金额、天数、人员、风险、事项等级、是否上报、是否上会等配置时，按配置调整审批目标；
5. 形成最终目标层级 `T'`。

审批层级不得由页面固定值或业务名称判断。

## 4. 审批路径的底层计算

路径必须由数字化属性和模型·数字化库逐级推演，不得在代码中预设“部长→分管领导→负责人”固定数组。

### 4.1 路径起点

`E → 人员信息数字化库 → 人员组织岗位配置 → A0 + N0`

取得申请人的组织层级、组织名称和岗位，作为当前组织。

### 4.2 当前组织内选人

按当前组织的组织性质、组织层级读取路径规则数字化库，从该组织规则规定的最小应审批职级开始，在人员组织岗位配置数字化库中匹配具体审批人。

### 4.3 是否达到最终目标

将当前审批节点的组织数字化属性与 `T'` 比较：

- 已达到最终目标：停止行政路径向上计算；
- 未达到最终目标：读取组织关系数字化库，进入上级/分管组织。

### 4.4 进入新组织必须重新计算

进入一个新的上级/分管组织后，必须把该组织作为新的当前组织，重新读取该组织自己的路径规则和内设职级规则，从该组织规定的最小应审批职级重新开始匹配。

禁止把下级组织的职级顺序直接延续到上级组织。

### 4.5 技术审查路径

技术/业务审查路径独立生成：

`M → 岗位分选数字化库 → 审查岗 → 审批路径数字化库 → 人员组织岗位配置数字化库 → 技术审查节点`

行政审批路径和技术审查路径按配置串联/插入/并联；需要形成单一顺序路径时，按配置拼接后以实际人员去重，重复人员保留靠后的有效环节。

## 5. 规定时限不是固定字段

办理记录中的“规定时限”必须是审批模型运算结果。

对每一个已经生成的审批/审查节点：

`节点类型 + 审批层级/岗位 → 审批层级配置数字化库 → 审批内容 + 规定时限 + 提醒规则 + 输出字段`

因此：

- 不同业务可能生成不同路径；
- 同一业务因阈值不同可能生成不同层级；
- 不同节点因节点类型、层级、岗位不同，规定时限可以不同；
- 规定时限不得写死在 React 页面、待办记录或业务模型代码中。

每个节点至少保存：到达时间、规定时限、应完成时间、实际提交时间、是否超时、提醒状态。

## 6. 办理记录必须解释“怎么计算出来的”

审批模型详情中的办理记录至少展示或可追溯：

- 当前节点类型；
- 当前审批/审查人；
- 当前审批层级/岗位；
- 路径来源规则；
- 命中的业务数字化属性；
- 命中的业务数字化标识/阈值；
- 基础审批目标 `T`；
- 调整后目标 `T'`；
- 当前组织与组织关系跳转；
- 本节点审批内容；
- 本节点规定时限及来源配置；
- 到达/提交/超时时间；
- 审批意见和结果。

页面不得只显示一条固定“路径”和一条固定“时限”而没有计算依据。

## 7. 审批结果与智选

逐环节审批完成后形成审批模型结果并写入审批模型数字化库。审批模型数字化库正式入库后，再通过硬性链接触发智选模型。

智选模型根据业务数字化标识、审批结果及关联配置决定后续模型。业务审批页面不得直接启动后续业务模型。

## 8. 验收要求

必须用至少两种结构明显不同的业务模型验证同一个审批模型：

1. 两种业务都能动态显示各自业务内容；
2. 审批页面没有任何请休假专属字段依赖；
3. 同一业务改变数字化标识阈值后，目标层级/路径随配置变化；
4. 进入上级组织时负责人路径按新组织规则重新计算；
5. 不同节点的规定时限从配置数字化库匹配获得；
6. 办理记录能够还原路径和时限的计算依据；
7. 审批完成后由审批数字化库触发智选，而不是前端直接调用。

# 07 通用审批与智选规则

## 1. 通用审批原则

审批应由通用审批模型/引擎承担，业务模型向审批传递业务模型文件名及审批所需参数，不为每个业务复制独立审批程序。

## 2. 审批基本顺序

- 接收业务模型文件名，并读取该文件名对应的业务运行记录；
- 从对应数字化库读取数字化配置、审批层级、人员信息、审批时限等数据；
- 先按阈值筛选，再按审批层级逐级计算；
- 处理会签、去重、跳过及上会等规则；
- 记录每一步审批意见与时间；
- 形成审批结果并写入审批数字化库；
- 入库后启动智选。

## 3. 审批结果规则

审批过程必须区分：

- 不同意并终止；
- 同意且流程结束；
- 同意但尚有下一审批环节；
- 阶段性上会后形成可入库结果并继续后续链路。

不得使用含义模糊的中间数值替代明确状态。

## 4. 智选判断顺序

智选启动后应按统一规则完成统计、审批结果判断、特殊情形判断、正常关联判断和模型触发。具体配置由数字化标识与模型关联关系决定。

## 5. 多标识触发

逻辑要求：

1. 计算需处理的数字化标识集合；
2. 筛选存在模型关联的标识集合；
3. 对每个有效关联标识统计其有效数据条数；
4. 按每条有效数据展开待触发的模型运行；
5. 形成最终触发集合并逐一启动；每次模型运行生成自己的模型文件名。

## 6. 特殊与正常规则

存在会议、统计分析、岗位接收人等特殊规则时，应“先特殊、后正常”；不得让普通关联提前吞掉特殊分支。

## 7. 配置来源

审批层级、审批人员、时限、会议类型、标识关联等，原则上均来自相应模型的数字化库，而不是散落代码常量。
