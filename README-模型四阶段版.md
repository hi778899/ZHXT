# 智慧企业治理系统 · 模型四阶段可运行版

本版本在原“驾驶舱生产环境版”代码上直接修改，不是静态原型。模型建设数据写入 PostgreSQL，用户可以在系统内实际完成“建议 → 设计 → 测试 → 配置/发布”四个阶段，并将发布后的模型直接作为可发起模型运行。

## 已实现

- **模型建议阶段**：模型名称、分类、类型、责任部门、目标、适用范围，以及人工、智选、定时、定量、硬性链接五类启动方式。
- **模型设计阶段**：已升级为低代码表单设计器 V2，采用“左侧组件库 + 中央所见即所得画布 + 右侧字段属性”的设计器结构；支持单行文本、多行文本、下拉、日期、数字、是否、人员等字段，字段可拖拽排序、复制、删除、设必填、配置来源/提示语/选项，并提供电脑/手机画布预览。
- **模型运行结构**：单个模型内部可配置交互、读取、参数、运算、判断、输出存储节点；审批不是业务节点，而是独立模型，通过配置阶段的模型关系在前序模型归档后触发。
- **模型测试阶段**：测试用例保存在数据库，服务器使用与正式运行相同的校验、运算和规则引擎执行；测试不通过不能发布。
- **模型配置阶段**：配置模型数字化编码、FN 文件名前缀、逻辑数字化库名称、固定 L 数字化标识、启动方式和后续模型；发布后进入“可发起模型”。
- **一个模型一个数字化库**：模型运行记录进入 `model_runs`，模型数字化结果同时进入 `digital_library_records`，按模型、逻辑库名、固定数字化标识和 FN 文件名区分。
- **请休假模型**：系统初始化即提供一套已发布的请休假模型；也可在“模型建设”中选择“请休假模型模板”，从建议阶段开始修改，重新测试并发布。运行界面直接读取设计阶段字段，不再写死请假表单。
- **数字化标识规则**：L 标识是固定的数据存储识别单元，不再为每次运行生成新的 L；每次运行由 FN 文件名和运行记录区分。

## 零代码工作台 V4（2026-09-06）

- **React Flow 自由连线**：`模型运行结构` 不再是顺序列表。节点可以自由拖拽，支持画布缩放、平移、MiniMap、连线/删线；判断节点具有“是/否”两个独立出口，连线名称可编辑。
- **发布前图校验**：服务器检查起点数量、不可达/孤立节点、普通节点多出口、判断节点重复分支、输出节点继续向外连接和有向环，避免把无效流程发布为模型。

## V5：独立审批模型架构（2026-09-06）

V5 对 V4 的模型边界进行了架构修正：**审批不再作为业务模型内部节点**。单个模型内部画布只描述本模型自身的运行结构，通用节点为“交互、读取、参数、运算、判断、输出存储”。跨模型关系统一放到第 4 阶段“配置”中。

请休假业务链现在是：

```text
请休假模型
  交互输入 → 读取人员/组织 → 计算请假天数 → 输出存储/归档
       ↓（模型完成归档后，硬性链接）
审批模型
  读取前序归档 → 形成审批参数 → 计算审批路线 → 逐级审批交互 → 审批结果归档
```

其中“审批模型”本身也是一个完整的四阶段模型建设项目，而不是 React Flow 节点。审批模型默认使用 `hard_link` 启动，因此不出现在普通用户“可发起模型”入口；只有配置为 `manual` 的模型才对人工发起开放。

服务器运行规则同步修改：业务模型只有在本模型数字化库完成归档后，才根据 `afterArchiveEnabled + nextModelName` 触发下一独立模型。触发时传递前序模型名称、FN 文件名、固定 L 数字化标识、输入/输出和运行 ID。审批模型的待办通过 `todos.run_id + step_index` 与审批模型运行实例绑定，逐级审批完成后才形成审批模型自己的归档结果。

数据库升级新增 `server/migrations/005_independent_approval_model.sql`，同时修正 `query_records.digital_id` 的旧唯一约束：L 标识是模型数据类的固定标识，同一模型的多次运行允许使用同一 L 标识，实例唯一性由 FN 文件名和 `runId` 区分。

## V6：全模型统一四阶段建设（2026-09-06）

V6 根据《模型·库推演技术总结20260820》再次收敛系统建设逻辑：**业务模型、审批模型、智选模型以及会议模型簇中的每一个模型，都必须作为独立模型·库，通过同一个“建议 → 设计 → 测试 → 配置/发布”工作台建立。** 模板只提供推演初值，不代表系统写死了该业务流程。

V7 起设计阶段不再显示“模型标准表达结构”六列表。模型建设直接通过表单设计器、运行节点、参数、运算、公式、规则、测试和配置完成；React Flow 仍只描述单个模型内部程序处理结构，不承载跨模型编排，也不存在审批节点。

“可发起模型”和具体发起页面面向业务使用者，隐藏模型节点、数字化库、数字化标识、跨模型关系和建设机制等技术说明，只展示实际需要填写的字段与提交操作。

第 4 阶段的模型关系从单一 `nextModelName` 升级为 `relations[]`，支持多条：

- `hard_link`：本模型完成规定处理、数字化库确认数据后固定启动目标模型；
- `smart`：依据已确认输入/输出数据和条件配置选择目标模型。

服务器保留对 V5 `afterArchiveEnabled + nextModelName` 的兼容读取，但新工作台统一写入 `relations[]`。请休假模板默认硬性链接审批模型；审批模型默认硬性链接智选模型；智选模型不再预置某个固定后续模型，由用户在配置阶段建立实际关联规则。

新增 `server/src/model-templates.ts`，统一提供 13 个四阶段模板：空白、请休假、审批、智选，以及会议议题提报、会议收集、会议议题编组、会议议题审定、会议组织、会议通知、参会反馈、会议、会议纪要。会议模型簇初始化为草稿建设项目，不自动发布、不由服务器写死先后关系。

详细说明见 `V6-全模型四阶段建设与模型簇说明.md`。

## V12：智选模型待办可见性

审批模型归档后固定触发智选模型。智选模型自动完成后续模型判断并按配置触发目标业务模型，同时向原业务发起人生成一条“智选结果”待确认记录；该记录只用于查看系统智选结果，不改变智选的自动运行属性。用户确认查看后，该记录进入“我的已办”。

## V13：审批归档可见与智选标识关联

- 用户人工发起的业务模型仍在“我的已办”中显示；其独立审批模型最终归档后，发起人的“我的已办”同时增加审批模型归档记录。
- 智选模型以最初业务模型为智选对象，保留业务模型文件名 FN 和业务数字化标识，并形成“关联数字化标识”集合。
- 请休假模型当前只有“业务归档 → 审批模型”的硬性链接，没有配置任何智选关联业务模型。因此智选模型显示关联数字化标识“无”，判断结果为“本模型（请休假模型）没有后续关联的模型”，不触发新业务模型。

## V14：16位数字化编码与双文件名

V14 按最新编码口径将内置模型数字化编码、人员数字化编码、数字化标识统一校核为16位数字。模型运行的系统文件名统一生成为“模型数字化编码-发起人人员数字化编码-时间码”，同时保存面向用户的中文显示名称“模型中文名称-发起人姓名-时间码”。请休假模型示例为 `5011001005001002-5011002000000001-20260908140000`，中文显示名称为 `请假模型-张珊-20260908140000`。

智选模型保留最初业务模型的系统文件名、中文显示名称、16位数字化标识和关联数字化标识。当前请休假模型未配置智选后续关联模型，因此关联数字化标识和后续关联模型均显示为“无”。升级由 `server/migrations/011_16_digit_codes_and_display_filename.sql` 完成，不清空已有数据库。
