# 00 项目总规则

## 1. 系统定位

智慧企业治理系统是以“模型·库”为基本运行颗粒构建的企业治理平台。系统中的审批、会议、请休假、驾驶舱、人员信息、数字化配置等能力，原则上均通过统一的模型建设、数字化配置和模型运行机制形成，而不是为每个业务单独堆叠不可复用的页面与代码。

## 2. 最高级业务原则

### 2.1 一模型一数字化库

每个模型必须且只能对应一个本模型数字化库。模型运行形成的有效结果，只能写入该数字化库。

### 2.2 模型簇

需要治理流转的业务模型，统一通过模型簇运行：

`业务模型 → 审批模型 → 智选模型 → 关联业务模型`

其中：

- 业务模型完成运行并将正式结果写入本业务模型对应数字化库后，由该数字化库按硬性链接规则触发审批模型，并传递业务模型文件名；
- 审批模型完成运行并将审批结果写入审批模型对应数字化库后，由该数字化库按硬性链接规则触发智选模型，并传递审批模型文件名；
- 智选模型读取业务结果、审批结果和数字化关联规则，确定后续需要启动的模型运行；每次被启动模型运行均生成自己的模型文件名。

### 2.3 数字化三要素

系统数字化表达统一围绕：

- 数字化编码：确定模型及数字化对象身份与唯一性；系统不另设模型 ID；
- 属性：描述对象类别、特征和计算所需属性；
- 标识：表达有效运行结果、状态和关联触发条件。

当前数字化结构按对象分别编码：模型19位、员工11位、业务分类属性19位、数字化标识19位、组织数字化属性12位、组织名称数字化属性12位；具体结构以 `04_DIGITALIZATION_RULES.md` 当前有效规则为准。

> 【历史口径已作废】原“统一16位数字化结构”仅用于历史数据兼容，不再约束新建数据。

### 2.4 四阶段模型建设

模型必须通过四个建设模型逐级形成：

1. 业务定义模型
2. 数字化定义模型
3. 模型设计模型
4. 模型发布模型

这四个阶段不是四个页面步骤，而是四个可运行的建设模型。每个建设模型自身同样遵循“一模型一数字化库”，并按“建设模型 → 审批模型 → 智选模型”的模型簇完成本阶段确认与下一阶段触发。四个建设模型均必须在系统中可填写、可保存、可恢复、可修改、可追溯。不得要求用户每次修改目标模型都重新修改源代码。

### 2.5 所有可选数据均来自数字化库

系统所有模型对应的库统一称为“数字化库”，不另设其他库分类。凡出现下拉框、单选、多选、人员选择、部门选择、会议类型、审批层级等需要引用既有数据的字段，默认必须从相应模型运行形成的数字化库读取。多个字段、多个模型可以共享读取同一数字化库，但不得复制数据形成另一套静态枚举。

## 3. 平台与业务的边界

平台代码负责：

- 模型建设器
- 表单/界面设计器
- 数字化配置器
- 模型运行引擎
- 审批引擎
- 智选引擎
- 数据源引擎
- 权限体系
- 审计体系
- 数据库迁移
- 发布运行机制

业务模型配置负责：

- 字段
- 界面
- 规则
- 数据来源
- 数字化标识
- 审批关联
- 智选关联
- 触发方式
- 输出内容

除平台能力不足需要扩展平台机制外，新增一个普通业务模型不应要求复制一整套新的前后端代码。

## 4. 修改原则

- 采用增量修改，不重写整个项目。
- 先复用已有通用能力，再增加新能力。
- 只修改本需求必要范围。
- 保持历史已发布模型可运行。
- 数据结构变化必须可迁移、可回滚或有明确回退策略。
- 模型定义与模型运行数据分离。
- 草稿配置与已发布版本分离。

## 5. 规则文件优先级

本文件是业务规则总纲；专项规则对具体领域具有更高约束力，但不得与本总纲冲突。
