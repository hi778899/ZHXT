# 08 模型运行引擎规则

## 1. 引擎职责

运行引擎负责把“已发布模型定义”解释为实际模型运行，包括：

- 依据模型数字化编码加载模型定义；
- 创建本次模型运行上下文；
- 生成本次模型文件名；
- 加载模型版本；
- 读取输入及所需外部数字化库；
- 执行校验；
- 执行运算/规则；
- 生成输出；
- 生成数字化标识；
- 形成以模型文件名识别的运行记录；
- 写入本模型数字化库；
- 将正式运行结果写入本模型对应数字化库；由数字化库在确认有效入库后执行硬性链接触发或其他基于数字化库的触发规则；
- 记录日志与审计。

## 2. 唯一性与运行记录

模型唯一性由数字化编码确定，不使用模型 ID。

模型每运行一次必须形成一个新的模型文件名；该文件名是本次运行记录的识别依据。上下游模型通过来源模型文件名追溯并读取上一环节运行记录，不使用实例 ID 作为业务链路依据。

## 3. 运行版本固定

运行开始时必须记录所使用的具体模型版本。模型后续发布新版本时，不应静默改变已经开始运行记录所对应的规则。

## 4. 幂等性

关键触发应具有幂等控制，避免网络重试或重复点击对同一来源模型文件名产生不应存在的重复审批、重复智选或重复入库。

## 5. 事务边界

“模型文件名运行记录形成”“结果正式写入本模型对应数字化库”与“数字化库触发下一模型”的一致性必须有明确设计。硬性链接的触发主体必须是完成有效入库的数字化库，不得由上一步模型在入库前直接调用下一模型。应防止出现已入库但数字化库未触发、已触发但上一步运行记录未完整形成，或模型直接调用造成数字化库状态与模型链路不一致的半完成状态。

## 6. 定时启动

定时计划与定时执行应分离：计划模型生成待启动任务，执行器按计划触发；每次实际运行仍必须生成本次模型文件名并形成运行记录。配置读取应来自数字化配置，不在代码中固定时间表。

## 7. 定量启动

定量触发必须按增量或已触发快照计算，不能简单判断“总数 >= 阈值”后永久反复触发。每次实际触发的模型运行均生成独立模型文件名。

## 8. 失败处理

失败至少记录：

- 模型数字化编码
- 模型文件名（已生成时）
- 模型版本
- 来源模型文件名
- 输入摘要
- 错误类型
- 错误位置
- 技术追踪信息
- 是否可重试
- 已执行步骤

不得静默吞错。
