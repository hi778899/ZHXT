# 06 数字化库与数据源规则

## 1. 唯一库概念

系统只使用“数字化库”这一库概念，不另设其他库分类。

所有数字化库均由模型唯一对应并通过模型运行形成、维护数据：

`模型 → 运行 → 本模型数字化库`

当其他模型需要引用这些数据时，通过数据源配置读取对应数字化库：

`模型 A ← 数据源配置 ← 模型 B 数字化库`
## 1.1 模型业务数据唯一正式来源

模型业务数据的唯一正式来源是其归属数字化库。`model_runs`、`run_id`、模型文件名、待办记录等只负责运行身份、状态、关联和追溯，不得替代数字化库成为业务字段的最终展示来源。

统一读取链路：

`run_id / 模型文件名 → 定位模型运行 → 定位对应数字化库 → 按数字化标识读取正式数据 → 页面展示/后续模型使用`

因此：

- 业务模型字段读取业务模型数字化库；
- 审批结果、审批办理结果读取审批模型数字化库；
- 智选判断与关联启动结果读取智选模型数字化库；
- 规定时限读取模型时限数字化库；
- 人员、组织、业务分类、审批分管等分别读取其对应数字化库；
- `todo.content`、`model_runs.input_data/output_data` 可作为运行过程留痕或历史兼容定位信息，但不得作为当前正式业务数据源。


例如，人员选择读取“人员信息模型”的数字化库；部门选择读取“组织/部门模型”的数字化库；会议类型、审批层级、审批时限、数字化配置等也分别读取其对应模型的数字化库。

### 1.2 审批目标的数据来源

审批模型的基础审批目标不是业务模型自身的固定属性，也不是前端默认值。正式来源必须是审批相关数字化库的动态匹配结果。

统一读取链路：

`来源业务模型数字化编码 → 模型数字化配置数字化库 → 业务分类数字化属性 → 审批分管配置数字化库 → 基础审批目标`

规则：

- “请休假”“考勤管理”等业务名称不得直接对应固定审批层级；
- 历史初始化中的“考勤管理 → 四级”等示例关系不得用于新运行；
- 审批阈值数字化库只负责在基础审批目标形成后进行调整，不负责凭空生成默认层级；
- 基础审批目标必须包含可追溯的组织层级、岗位/职务属性及对应数字化标识；
- 若数字化库没有匹配到唯一有效目标，返回“未匹配到基础审批目标配置”，不得从代码常量、历史运行快照或旧示例记录补值。

## 2. 需要绑定数字化库的数据场景

凡字段的数据不是由当前用户自由输入，而是需要从系统既有数据中选择、查询或联动取得，都应通过数据源绑定相应数字化库，例如：

- 下拉框
- 单选
- 多选
- 人员
- 部门
- 岗位
- 组织
- 会议类型
- 审批层级
- 业务意见项
- 业务类别
- 状态分类
- 数字化配置项
- 其他模型运行结果

## 3. 一处形成，多处读取

一项业务数据只能由其归属模型负责形成并写入本模型数字化库。其他模型如需使用，应读取该数字化库，不应复制形成另一份静态数据。

多个模型、多个字段允许同时读取同一数字化库。例如请休假、审批、会议等多个模型均可读取人员信息模型数字化库中的人员数据。

## 4. 数据源配置

字段数据源至少应描述：

- 来源模型
- 来源数字化库
- 查询条件
- 显示字段
- 值字段（需要跨模型稳定关联时优先使用相应数字化编码）
- 排序规则
- 有效数据筛选条件
- 依赖字段
- 权限过滤
- 数据版本或生效条件（如业务需要）

数据源本身应由模型配置保存，不得只存在于前端临时状态。

## 5. 禁止硬编码和复制数据

禁止：

- 在 React/Vue 等组件中写固定人员、部门、会议类型等业务列表；
- 在后端代码中维护业务枚举来替代应由模型数字化库提供的数据；
- 每增加一个数据项就修改并发布代码；
- 将其他模型数字化库的数据复制一份作为当前模型长期维护的数据源；
- 使用显示名称、模型 ID 或实例 ID 作为跨模型稳定关联依据；模型身份使用数字化编码，运行记录使用模型文件名。

## 6. 数字化配置本身也遵循一模型一数字化库

数字化配置、审批配置、智选配置、人员信息、组织信息、会议类型、审批层级、审批时限等基础数据，同样必须由相应模型建设、运行并形成对应数字化库，不得因为属于“系统配置”就绕开“一模型一数字化库”。

## 7. 写入边界

读取其他模型数字化库不代表拥有写入权限。模型只能将本次运行形成的正式结果写入本模型数字化库。

若需要改变另一个数字化库中的业务数据，应启动其对应模型，通过该模型运行完成变更并形成新的有效结果，禁止跨模型直接写库。
