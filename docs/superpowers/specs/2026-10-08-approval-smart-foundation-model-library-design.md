# 审批/智选基础模型库运行入库设计

## 目标

把审批模型、智选模型依赖的基础数据统一纳入“一模型一数字化库”治理：基础数据的初始化、同步和可确定的自动补齐必须形成对应生产模型的真实 `model_runs`，再归档进入对应数字化库；不得新增通过 seed/migration 直接写正式 `digital_library_records` 的补丁。

## 核心原则

1. 审批/智选只读取正式数字化库，不读取 seed 常量、`model_runs.input/output` 或 todo 内容作为正式业务配置。
2. 每个基础数字化库必须绑定唯一数据产生模型；系统维护基础数据时必须先形成该模型运行，再入库，正式记录 `run_id` 不得为空。
3. `system_initialization` 仅用于首次建立审批可启动的最小闭环，避免“基础模型数据要审批、审批又依赖基础数据”的循环；仍必须形成真实模型运行。
4. 最小闭环就绪后，人工新增/修改基础配置继续走正常“基础模型 → 数字化库 → 审批 → 智选”模型簇。`system_sync` 只同步已有系统事实或可唯一推导的数据，不得猜测业务事实。
5. 无法从现有正式数字化数据唯一确定的配置不自动编造，记录完整性问题并只阻止相关模型运行，不阻断整个应用启动。
6. 历史 migration 中的 0622 直接数据只作为历史初始化来源；通过既有物化机制转为真实模型运行后继续使用。今后的 migration 不再新增正式基础业务数据记录。

## 基础模型库注册表

### 审批模型运行硬依赖

| 数据产生模型 | 数字化库 | 要求 |
|---|---|---|
| 模型数字化配置模型 | `lib-standard-digital-config` | 至少一条正式运行数据；来源模型必须有匹配配置 |
| 审批分管配置模型 | `lib-standard-approval-assignment` | 至少一条正式运行数据 |
| 员工信息模型 | `lib-standard-person` | 至少一条正式运行数据；当前发起人另做精确匹配 |
| 组织名称数字化模型 | `lib-standard-dept` | 至少一条正式运行数据 |
| 组织关系模型 | `lib-digital-org-relationship-0622` | 至少一条正式运行数据 |
| 模型时限模型 | `lib-standard-model-timeout` | 至少一条正式运行数据；人工配置仅审批同意后生效 |
| 审批意见标准模型 | `lib-standard-approval-opinion` | 至少一条正式运行数据 |

### 审批配置支撑库

| 数据产生模型 | 数字化库 | 用途 |
|---|---|---|
| 业务分类模型 | `lib-digital-business-classification-0622` | 模型业务分类数字化属性 |
| 组织数字化模型 | `lib-standard-org-rank` | 组织数字化属性/岗位属性 |
| 业务归属模型 | `lib-standard-business-ownership` | 组织业务领域 |
| 员工数字化模型 | `lib-digital-employee-code-0622` | 员工数字化编码 |
| 阈值类属模型 | `lib-standard-threshold-type` | 阈值类型维护 |
| 审批阈值配置模型 | `lib-standard-threshold-config` | 阈值配置维护；当前相对级次规则不恢复绝对组织层级语义 |

### 智选模型运行硬依赖

| 数据产生模型 | 数字化库 | 要求 |
|---|---|---|
| 模型数字化配置模型 | `lib-standard-digital-config` | 正式运行数据 |
| 标识关联配置模型 | `lib-standard-identifier-trigger` | 库/生产模型必须就绪；允许 0 条关联数据，0 条表示本次没有后续关联，不得伪造 |

### 智选配置支撑库

| 数据产生模型 | 数字化库 | 用途 |
|---|---|---|
| 数字化标识建设模型 | `lib-standard-identifier` | 标识关联配置候选标识 |
| 模型信息标准模型 | `lib-standard-model` | 后续目标模型候选项 |

## 模型运行入库通道

系统提供统一的“模型支撑数据运行入库”函数。调用方提交：目标数字化库、稳定幂等键、运行人员、数字化标识值、正式数据、来源、启动模式。该函数必须：

1. 从数字化库反查唯一生产模型；
2. 验证生产模型存在已发布项目及当前 19 位模型数字化编码；
3. 生成 `模型数字化编码-员工数字化编码-时间码` 文件名；
4. 创建真实 `model_runs`，`trigger_mode` 为 `system_initialization` 或 `system_sync`；
5. 将本次运行输出归档到该模型唯一数字化库，并写入 `run_id`；
6. 同一幂等键且数据未变化时不重复产生运行；数据变化时形成新的真实运行并更新当前正式记录；
7. 不允许调用方直接 `INSERT digital_library_records` 代替上述过程。

## 就绪校验

新增审批/智选基础模型库就绪校验：

- 校验数字化库存在且启用；
- 校验库绑定的数据产生模型与注册表一致；
- 校验生产模型有已发布项目和当前 19 位模型数字化编码；
- 对要求非空的硬依赖校验有效记录数；
- 对正式记录校验 `run_id`；
- 标识关联配置数字化库允许 0 条记录，但模型和库结构必须就绪。

审批模型进入 0622 当前结构计算前执行 `ApprovalBaseReady`；智选模型进入当前结构计算前执行 `SmartSelectBaseReady`。失败提示必须明确“缺失基础模型、数字化库、缺失原因”，不得只报“未匹配到配置”。

## 自动补齐边界

系统可以自动运行模型补齐以下可唯一确定的数据：

- 已发布模型的模型数字化配置（业务分类可以从现有正式类别映射唯一确定时）；
- 系统已存在组织/人员事实的员工编码、员工信息同步；
- 现有正式业务域扩展对应的基础审批分管/通用时限基线；
- 已有 0622 历史基础数据的模型运行物化。

如果业务分类、审批分管人、智选目标关系等不能唯一确定，则生成问题记录，不自动猜测。

## 初始化顺序

`模型/基础模型项目就绪 → 历史基础数据物化为 system_initialization 模型运行 → 可确定基础数据通过对应模型运行补齐 → 员工数字化配置同步 → 审批/智选基础库就绪审计 → 正常业务服务启动`

就绪审计发现问题时只记录并阻止相关模型，不使整个应用退出。

## 验收

1. 所有新增基础数据完善路径都能追溯到对应 `model_runs`，正式库记录 `run_id` 非空。
2. seed、员工同步、模型配置完整性补齐使用统一模型运行入库通道。
3. 审批启动前可明确列出缺失的基础模型库；智选同理。
4. 标识关联配置为空时智选正常完成“无关联”，不得伪造数据。
5. 绝对组织层级不得重新成为审批级次；现有相对审批/审查级次规则保持不变。
6. 历史 0622 数据继续兼容，但 0622 只作为初始化来源/版本，不作为绕过模型运行的理由。
