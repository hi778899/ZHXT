## 二、分支规范

`main` **只存放当前正式稳定代码，禁止日常开发直接提交。**

| 分支类型 | 用途 | 命名示例 |
|---|---|---|
| `feature/<name>` | 新增能力 | `feature/model-library-scope` |
| `fix/<name>` | 普通缺陷修复 | `fix/approval-timeout-value` |
| `hotfix/<name>` | 生产紧急修复 | `hotfix/login-crash` |
| `refactor/<name>` | 经批准的架构整理 | `refactor/digital-codes` |

### 标准开发流程

```bash
# 1. 从最新 main 建分支
git checkout main
git pull origin main
git checkout -b feature/your-feature

# 2. 开发并提交
git add -A
git commit -m "feat(model-library): 补充全部库范围筛选"

# 3. 推送分支
git push -u origin feature/your-feature

# 4. 在 GitHub 发起 Pull Request，评审后合并 main
# 5. 合并后删除临时分支
```

> 下一项需求必须**重新从最新 main 建分支**，不从已完成旧分支继续叠加。
> 多分支并行时，提交 PR 前必须同步最新 main 并重新测试。

## 三、Commit 规范

格式：`<类型>(<模块>): <变更目的>`

| 类型 | 含义 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 缺陷修复 |
| `chore` | 构建/依赖/仓库维护 |
| `refactor` | 重构 |
| `docs` | 文档变更 |
| `test` | 测试变更 |

示例：

- `feat(model-builder): add digital library data source`
- `fix(approval): prevent duplicate countersign trigger`
- `chore(db): add migration for model version table`

## 四、Tag 与版本发布

正式发布在 `main` 对应 commit 上打 Tag。

```bash
git checkout main
git pull origin main
git tag -a v0.17.7.26 -m "V17.7.26 版本说明"
git push origin v0.17.7.26
```

Tag 命名与项目版本号对应：`V17.7.25` → `v0.17.7.25`。
**历史版本依赖 Tag + Commit 保存，不通过长期保留大量旧分支保存。**

---

## 五、PR 要求

Pull Request 至少包含：

1. 需求 / 问题
2. 实现方案
3. 变更范围
4. 数据库变化（是否新增 migration）
5. 测试结果
6. 风险
7. 截图或运行证明（UI 变更时）

## 九、新版本入库流程

拿到新的交付 zip 后：

```bash
# 1. 归档（命名：工作台版本__模型版本__.zip）
cp "新版本.zip" "E:/代码同步/GitHub/ZHXT-版本归档/原始交付包/V17.7.28__18.3.6.32__.zip"

# 2. 解压覆盖工作区（-o 覆盖同名文件，不删除多余文件）
cd E:/代码同步/GitHub/ZHXT
unzip -o -q "E:/代码同步/GitHub/ZHXT-版本归档/原始交付包/V17.7.28__18.3.6.32__.zip" -d .

# 3. 恢复 README 顶部导航区块（会被版本 README 覆盖）
#    见本目录 README-HEADER 模板，或手动补回

# 4. 提交并打 tag
git add -A
git commit -m "feat(<模块>): V17.7.28 <变更摘要>"
git tag -f v0.17.7.28

# 5. 推送
git push origin main --tags
```

> `unzip -o` 只覆盖同名文件、不删除多余文件，因此像 `docs/superpowers/`、
> `docs/development/仓库管理规范.md`、`.gitignore` 这类仓库侧内容会自动保留。
